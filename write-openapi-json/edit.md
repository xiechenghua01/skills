# 编辑链

改已有的契约文件：审、改、挪。**新增一个 operation 走 [generate.md](generate.md)**；本链只管已经存在的路径与字段。

```
判模式 → 记基线 → 诊断 / 修订 / 迁移 → 复检 → 交付
```

---

## Step 1 判模式

| 用户要什么 | 模式 | 动文件吗 |
|---|---|---|
| 审阅、查缺、看看这份契约有什么问题 | 诊断 | **不动**，只出清单 |
| 补字段、改描述、改 schema、改枚举、删接口、改路径 | 修订 | 动 |
| 挪到另一个文件、合并两份、拆分文件 | 迁移 | 动 |
| 判断不出 | 先问一句 | — |

诊断常常是修订的前半段：先出清单，用户确认要改哪些，再进修订。**未经确认不要在诊断后自动开改。**

---

## Step 2 记基线

**门禁。** 改之前先留一份可比对的基线：

```bash
python3 <skill 目录>/scripts/validate_openapi.py --json <文件>
python3 <skill 目录>/scripts/validate_openapi_request_contract.py --json <文件>
python3 <skill 目录>/scripts/validate_openapi_response_contract.py --json <文件>
```

记下每条命令的 `ok`、问题条数与规则码分布，以及当前路径清单（文件 → 方法 + 路径）。后面所有「有没有改坏」的判断都以这份基线为准：**改完的报错数不得多于基线**，新增的规则码必须逐条解释或修掉。

用 `--json` 而不是文本，是因为问题条数从文本里数出来的结果不可靠；结构化输出可以直接比对 `code` 序列。

---

## Step 3 诊断模式（只读）

脚本能抓的交给脚本，抓不到的四类靠人：

| 脚本抓不到 | 怎么判 |
|---|---|
| 字段与代码是否一致 | 回 Model / Resource / 分页器核对，不看旧文档 |
| 描述是否有业务含义 | 只写字段名或「字段」二字的，算不合格 |
| 枚举是否完整 | 对照代码里的常量与判断分支，含 `null` 与历史兼容值 |
| 范围是否正确 | 路径清单与用户指定范围逐条对 |

输出一张清单，不要散文：

| 文件 | 路径 | 位置 | 问题 | 依据（代码位置） | 建议 |
|---|---|---|---|---|---|

诊断模式下**不改文件、不顺手修**。清单交付即结束。

---

## Step 4 修订模式

只改命中范围，其余原样保留。

| 改动 | 额外约束 |
|---|---|
| 补字段 | 必须回代码确认类型、是否必填、是否可空、枚举取值；不能凭接口名推测 |
| 改描述 | 说明业务含义、单位、格式、枚举、长度、条件必填；改完提醒导入侧可能保留旧说明（见 [pitfalls.md](references/pitfalls.md)） |
| 改 schema | 可空与必填同步改；`const` 与 `example` 的类型和值必须一起改 |
| 删接口 | 先确认别处没有同路径残留；同步更新 `info.description` 与 `tags` 里的范围声明 |
| 改路径 | 同文件内不得与已有路径重复；路径参数名要与 `parameters` 一致 |

**不要重排无关字段、不要顺手格式化整份文件**——diff 会变得无法审阅，等于放弃了「范围准确」这个约束。

字段名保持代码里的真实拼写，即使拼写不规范。要说明就在 `description` 里说明，**不许改名**。

---

## Step 5 迁移与合并

| 动作 | 必须做到 |
|---|---|
| 迁移（A → B） | 写入 B、从 A 删除；检查 A、B 无重复路径；两文件的 `info.description` 范围和文件名同步更新 |
| 合并（A + B → C） | C 保留全部路径；A、B 删除；C 的文件名要覆盖合并后的全部业务范围，不能沿用只覆盖其一的旧名 |
| 拆分（A → B + C） | 新文件名各自表达子范围；A 删除已迁出的路径，保留未迁出的 |

**守恒校验（门禁）**：迁移前后接口总数不变，迁出数等于迁入数；合并后总数等于各文件之和减去重复路径数。对不上就说明有接口丢了或被写了两遍。

迁完把涉及的文件一起交给结构校验，它会顺带比对跨文件重复路径：

```bash
python3 <skill 目录>/scripts/validate_openapi.py <文件A> <文件B>
```

出现 `DUP-001` 就说明同一路径还在两份契约里，必须删到只剩一份。

---

## Step 6 复检与交付

1. 三条脚本重跑，error 数 ≤ 基线；新增的 error 必须修到清零。
2. 重新打印路径清单，与 Step 2 的基线对比，确认增减符合预期。
3. 全局搜 `components`、`$ref`、`security`、非 `200` 响应，确认没有在编辑中混进来。
4. 交付说明写四件事：改了哪些路径的哪些字段、基线对比结果、迁移守恒结论、仍无法从代码确认的缺口。

---

## 禁止

- 禁止借修订之名重写整份文件——那是重新生成，要回生成链重锁范围。
- 禁止改字段名、改路径参数名（除非代码确实改了）。
- 禁止为了让脚本通过而删字段、改类型、加镜像媒体类型。
- 禁止诊断模式下动文件。
- 禁止迁移后旧文件里还留着同路径接口。
- 禁止在没跑基线的情况下说「只改了一点点」。
