# 生成链

从代码写到契约文件。写**新的** operation 走本链；改已有的 operation 走 [edit.md](edit.md)。

```
锁范围 → 追踪代码 → 命名落位 → 建字段清单 → 编写 → 三脚本校验 → 对账交付
```

四道门禁：范围、追踪、字段清单、校验。任何一道不过就停，不要边写边补。

---

## Step 1 锁范围与文件归属

**门禁。** 动手前先产出一张清单，八列缺一不可：

| 业务域 | 目标文件 | 方法 | 路径 | Controller 方法 | Request 场景 | 参数来源 | 响应构造位置 |
|---|---|---|---|---|---|---|---|

文件归属规则：

| 用户说 | 规则 |
|---|---|
| 「单独一个文件」 | 只能写进该文件，不得追加到总文件或别的业务域文件 |
| 「合并到一个文件」 | 相关业务域只能进这一份，不得每个域再建一份 |
| 「从 A 挪到 B」 | 迁移后必须从 A 删除，并检查 A、B 无重复路径 |

写入前和写入后各打印一次路径清单，文件数、路径数、方法与清单逐项对齐。**结构校验通过不代表范围正确**——写进了错误的文件，属于失败。

范围里有互不相关的业务域或边界不清时，先问是否拆文件。

---

## Step 2 追踪代码

**门禁。** 顺着真实调用链读，不能只看 Controller 方法名。

| 要写的内容 | 追到哪里 |
|---|---|
| 路由与路径参数 | 路由定义文件 |
| 请求字段 | Controller → Request 的 `scene` / `validated()` → Service 实际取用的字段 |
| 响应字段 | Service 返回值 → Model 的 `$fillable` / `$appends` / `$hidden` / `$casts` → 关联关系 select 列 → Resource / 格式化方法 → 响应封装 → 分页器元数据 |
| 枚举与校验规则 | Request 规则 + Service 里的判断分支与失败提示 |

补充规则：

- 列表和详情响应必须追到**最终返回值**，完整展开嵌套对象、分页字段、可空字段；禁止用占位结构代替。
- 「当前有改动的接口」要同时看 Git diff 和完整代码，只看 diff 会漏掉未改动但相关的部分。
- 代码与需求冲突、动态字段无法确认时，停下来问，不要猜。
- 只复用已有接口的**说明风格和响应封装**，不复制与当前接口不一致的字段或旧模型。

---

## Step 3 命名与落位

规则见 [format-guide.md](references/format-guide.md)《文件命名》。三条最常错：

- 文件名必须覆盖**合并后的全部范围**，不能沿用只覆盖其中一个资源的旧名。
- 不用 `openapi.json`、`api.openapi.json`、`new.openapi.json` 这类无法表达范围的名称。
- 用户未指定目录：仓库有 `doc/` 就写 `doc/`，否则写当前文档目录。

---

## Step 4 建响应字段清单，再动笔

**门禁。** 在写 JSON 之前，为每个接口列一张响应字段清单：`$fillable`、`$appends`、`$hidden`、`$casts`、关联 select 列、Resource 附加字段、分页元数据。

清单里要显式登记三类容易被跳过的东西：

- `$hidden` 的字段（不输出，但要登记，否则对账时说不清）
- 格式化方法里**改了名**的字段
- 按场景裁剪的字段

没有清单就开始写，结果一定是「文档写了 10 个字段，接口实际返回 22 个」。

---

## Step 5 编写

按 [format-guide.md](references/format-guide.md) 写。三个容易写错的位置单独强调：

1. **媒体类型**：先判定接口真实怎么读参数——JSON body、`multipart/form-data`、表单、还是没有请求体。判定依据不明确时，在交付说明里写出判断过程和代码出处。
2. **示例位置**：完整请求示例在 `requestBody.content.<media>.example`，字段示例在字段自己的 `example`。两处都要有。
3. **可空 ≠ 缺省**：`required` 管「字段是否出现」，类型数组管「出现时能否为 null」。两者要分别声明，并写清新增与编辑场景的差别。

---

## Step 6 三脚本校验

**门禁。** 三条命令，全部通过才算交付：

```bash
python3 <skill 目录>/scripts/validate_openapi.py <文件>
python3 <skill 目录>/scripts/validate_openapi_request_contract.py <文件>   # 有 JSON body 或 multipart 时
python3 <skill 目录>/scripts/validate_openapi_response_contract.py <文件>
```

- 每条问题都带规则码（如 `RES-005`），修复时按码定位，不要靠复述文案。
- 同一业务域有多份契约时，`validate_openapi.py` 可一次传多个文件，它会额外比对**跨文件重复路径**（`DUP-001`）。
- 加 `--json` 输出结构化结果，便于机械对比修复前后的差异。

任何一步失败，修完必须**三条重跑**，不能只重跑失败那条。

失败先分类，再动手：

| 情况 | 处理 |
|---|---|
| 契约确实写漏或写错 | 按提示补齐，重跑 |
| 接口本来不是脚本假定的形态（纯 multipart、表单、纯二进制） | 保留与代码一致的真实契约，在交付说明里写清未通过项、原因与结论 |
| 脚本提示同一操作声明了两种媒体类型 | 回代码确认是否真的两种都支持；只支持一种就删掉另一种 |

**不许为了让脚本通过而改契约。** 补一个接口并不接受的 `application/json` 镜像，调用方按镜像传参会直接失败——这正是过去踩过的坑之一。

---

## Step 7 对账与交付

逐接口把 JSON 的 `properties` 与 Step 4 的清单对账：每个字段要么出现，要么逐条解释差异（`$hidden` 不输出、字段拆到别的接口按需查询）。**不允许静默缺失**，关联对象不许用空对象占位。

再确认四件事：

- 全局搜不到 `components`、`security`、`securitySchemes`、`$ref`、非 `200` 响应。
- 文件名能表达用户指定的全部范围。
- 旧文件没有残留路径或与新文件重复的路径。
- 路由清单与文件实际路径一一对应。

交付说明固定五要素：输出路径、覆盖的接口清单、请求示例位置、三脚本结果、仍无法从代码确认的缺口。

---

## 完成清单

- 范围清单八列齐全，写入前后各核对一次。
- 调用链追到响应构造处，不是只看了 Controller。
- 写之前建了响应字段清单，写之后逐条对账。
- 媒体类型按真实读取方式判定，没有补镜像。
- 三个脚本全过；有未通过项时已说明原因。
- 交付说明写了五要素，没有声称「已导入 Apifox」。
