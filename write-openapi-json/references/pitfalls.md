# 事故档案

> 每一条都是真实发生过的问题。写法固定：**病征 → 根因 → 防复发规则 → 现在靠什么挡**。
> 改动本技能前先读这份档案——这些坑每一条都复发过一次。
> 「现在靠」里标了规则码的，已由脚本机械拦截，可直接按码定位；写「人工」或「流程」的，仍要人按步骤做。

---

## 1. 响应字段大面积漏写

**病征**：接口实际返回 22 个顶层字段，文档只写了 10 个；关联对象用 `{}` 占位。
**根因**：没有从 Model 与格式化代码反推字段清单，凭旧文档和印象写。
**防复发**：写之前必须建响应字段清单（`$fillable` / `$appends` / `$hidden` / `$casts` / 关联 select / Resource / 分页器），写之后逐条对账，差异要逐条解释。
**现在靠**：生成链 Step 4 的门禁 + Step 7 对账。**没有规则码**——脚本只能查「写了但写错」，查不出「根本没写」，漏字段只能靠清单对账。

---

## 2. 响应侧缺中文说明，长期无人发现

**病征**：156 处响应字段、数组项、`oneOf` 分支没有中文 `description`；7 处 `code` 的 `example` 与 `const` 类型不一致；部分响应只写 `example` 不写 `schema`。
**根因**：请求侧有自动审计，响应侧只靠人工自觉。
**防复发**：响应必须有内联 `schema`；每个字段、数组项、联合分支都要有业务含义级说明；`const` 字段的 `example` 类型和值必须一致。
**现在靠**：`RES-003`（缺中文说明）、`RES-004`（只重复字段名）、`RES-005`（const 与 example 不一致）、`RES-002`（只有 example 没有 schema）。

---

## 3. Apifox 请求示例是空的

**病征**：结构校验通过，但导入 Apifox 后请求示例为空。
**根因**：只把字段放进 `schema.properties`，没写媒体类型级 `example`；或者写到了 `requestBody.example`、`schema.example`。
**防复发**：完整请求示例只能放在 `requestBody.content.<media>.example`，字段集合要与 `schema.properties` 完全一致（含可选字段）。
**现在靠**：`REQ-014`（示例字段集合与 properties 不一致）、`REQ-022`（缺媒体类型级示例）。

---

## 4. 字段「存在」但文档不可用

**病征**：字段有类型、有示例，但没有中文 `description`；或者描述只重复英文名。
**根因**：以为结构完整就等于文档可用。
**防复发**：每个字段都要说明业务含义、单位、格式、枚举、长度、条件必填；状态字段写清字段名和全部取值含义。
**现在靠**：`RES-003` / `REQ-018` / `PARAM-003`（三侧的中文说明检查）。

---

## 5. JSON Body 字段被塞进 parameters

**病征**：为了让界面显示字段，把 Body 字段复制到 `parameters`。
**根因**：误解 `parameters` 的语义。
**防复发**：`parameters` 只放 query / path；`parameters: []` 表示接口确实没有 query/path 参数，不表示漏了 `requestBody`。
**现在靠**：`REQ-012`（Body 字段重复出现在 parameters）。

---

## 6. 复用旧总文档追加新接口

**病征**：业务域归属错误，或同一路径在两个文件里各有一份。
**根因**：图省事，往已有大文件里追加，没先定目标文件。
**防复发**：先锁目标文件再动手；迁移必须从旧文件删除并检查两边无重复路径；文件名要覆盖合并后的全部范围。
**现在靠**：生成链 Step 1 的文件归属门禁 + Step 7 的残留路径检查；结构脚本一次传多个文件时会比对跨文件重复路径（`DUP-001`）。

---

## 7. 文件上传接口被补了 JSON 镜像

**病征**：接口真实只接受 `multipart/form-data`，契约里却多声明了 `application/json` 镜像；调用方按镜像传参直接失败。
**根因**：没先判定接口真实读取参数的方式，顺着脚本报错改契约。
**防复发**：媒体类型按代码判定；脚本报缺少 JSON 时先分类——是契约写错，还是接口本来就不是 JSON 形态。后者保留真实形态并说明。
**现在靠**：`MP-001` ~ `MP-010`（multipart 结构完整性）、`BODY-003`（媒体类型既非 JSON 也非 multipart）。

---

## 8. `items: {}` 让响应看似完整

**病征**：数组字段只写 `items: {}`，导入后展开不出字段。
**根因**：懒，或没追到数组元素的构造处。
**防复发**：能从代码确定结构就必须展开（附件要展开路径/大小/上传时间，等级选项要展开 `value`/`label`）；只有确认是动态结构才允许空 `items`。
**现在靠**：`REQ-015` / `RES-006`（items 空结构）。

---

## 9. 二次导入后中文说明没更新

**病征**：契约里改了字段说明，重新导入 Apifox 后界面还是旧文案。
**根因**：Apifox 的「智能合并」会保留旧文件里已编辑的中文名、参数说明、请求/响应示例；路径与方法相同时以已有数据为准。
**防复发**：改描述后，在导入时选覆盖模式，或在 Apifox 侧核对字段说明是否真的变了。**不要假设导一次就同步。**
**现在靠**：人工。脚本层看不到导入侧行为，已写入编辑链 Step 4 的改描述分支。

---

## 10. 文件编码或语法导致解析直接失败

**病征**：导入报解析错误，或脚本抛 `Unexpected UTF-8 BOM`。
**根因**：文件带 BOM、末尾多逗号、用了 Tab 缩进、或末尾没有换行。
**防复发**：UTF-8 无 BOM、两空格缩进、文件末尾留一个换行、JSON 不允许尾随逗号。
**现在靠**：`JSON-001`（解析失败）、`FILE-002`（非 UTF-8 或带 BOM）。能挡住，但报错文案不一定指向根因，所以规则写在 format-guide《文件与编码》。

---

## 冻结决策（别再翻案）

这三条被质疑过多次，结论已定，不要再改：

| 决策 | 理由 |
|---|---|
| 不写 `components` / `$ref`，字段全部内联 | 项目按业务域分文件维护，每份契约要能独立导入；抽公共模型会让单文件失去自解释性，也让「哪份文件覆盖哪些接口」变模糊 |
| 只写 `200` 响应 | 这份契约的用途是导入 Apifox 生成接口条目，错误码由实现侧的业务约定表达，写进契约只会和真实行为脱节 |
| 字段级示例用单值 `example`，不用 `examples` 数组 | 3.1 确实把 `schema.example` 标为 deprecated 并推荐 `examples` 数组，但现行契约已按 `example` 全量导入验证过；换成数组的导入效果未验证，收益为零、风险非零 |

要动这三条，先做一次真实导入验证，再改档案和 format-guide，别只改一处。
