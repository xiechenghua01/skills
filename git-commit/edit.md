# 编辑链

改一次**尚未推送**的提交。五种动作：补内容、改信息、拆分、合并、调顺序。

```
判类型 → 安全检查（门禁）→ 执行 → 等价校验（门禁）→ 收尾
```

具体命令序列见 [history-recipes.md](references/history-recipes.md)；改写后的信息写法仍按 [message-spec.md](references/message-spec.md)。

---

## Step 1 判类型

| 用户要什么 | 动作 | 结果 |
|---|---|---|
| 「漏了几个文件」「这个改动忘了加进去」 | 补内容 amend | 同一提交，文件集变大 |
| 「提交信息写错了」「标题改成…」 | 改信息 amend | 同一提交，仅 message 变 |
| 「太大了，拆成两个」 | 拆分 | 2 个以上提交，内容总和不变 |
| 「这几个 wip 合成一个」 | 合并 | 1 个提交 |
| 「顺序调一下」「把这个挪到前面」 | 重排 | 提交顺序变，内容不变 |

判不出就问一句，不要猜。**一次只做一种动作**：既要拆又要改信息时，先拆，再对每个新提交改信息。

---

## Step 2 安全检查

**门禁。四条逐条过，缺一条就停。**

1. **是否已推送**。`git branch -r --contains <hash>` 有输出即为已推送。
   - 已推送 → 说明后果（他人历史被改写、需要 force push），要用户明确授权；共享分支默认拒绝。
   - 仅本地 → 继续。
2. **工作区是否干净**。`git status --short` 有改动就先 `git stash` 或先提交。工作区不干净时做 `reset` / `rebase`，会把无关改动卷进去。
3. **目标提交是不是最新的几个**。不是最后一次提交的改写要重建历史，风险高一级；先确认用户知道。
4. **建安全网**：`git branch backup/<yyyyMMdd-HHmmss> HEAD`，并在报告里写下这个分支名。

`git reflog` 是最后兜底，但它不替代备份分支——reflog 会过期，也可能被后续 GC 清掉。

---

## Step 3 执行

- **只用非交互方式**。`rebase -i` 会打开编辑器，在无交互环境里必定卡死或改错。用 `reset --soft` + 重新提交、`--fixup` + `--autosquash`、或 `cherry-pick` 重建，配方见 history-recipes。
- **每一步之后立刻看形态**：`git log --oneline -n 8`，确认提交数量、标题、顺序符合预期，再进入下一步。
- 信息用 `-F -` 一次性传入，不用多个 `-m`。
- 钩子在 amend 与 rebase 时都会重新触发；失败就修根因，不绕过。

---

## Step 4 等价校验

**门禁。** 拆分与合并会重写提交，必须证明内容没变：

```bash
git diff backup/<时间戳>..HEAD     # 期望：空输出
```

- 空 → 内容等价，继续。
- 非空 → 有内容丢失或多出，立刻退回备份：`git reset --hard backup/<时间戳>`，重新做。

重排同理：提交集合相同、顺序不同，`git diff` 应为空。改信息（不改内容）时，比较 `git diff HEAD@{1}..HEAD` 同样应为空。

---

## Step 5 收尾

报告固定五项：改了几次提交、新历史长什么样（`git log --oneline` 片段）、是否已推送、备份分支名、怎么回滚。

- 内容等价校验通过后，备份分支保留到用户确认再删，不要自己 `branch -D`。
- 改写过的提交若原本已推送，提醒后续需要 `push --force-with-lease`，但**不要自己执行**。

---

## 禁止

- 禁止改已推送的提交而不告知后果、不要授权。
- 禁止在工作区不干净时 `reset` / `rebase`。
- 禁止跳过 Step 4 的等价校验就说「改好了」。
- 禁止 `--no-verify` 绕过钩子。
- 禁止用交互式命令（`rebase -i`、`add -p`、`commit --interactive`）。
- 禁止把「拆分」做成「删掉原提交、凭记忆重写一遍」——必须从原提交的内容出发。
