# 提交信息规范

> 两条链共用。生成链 Step 6 按它写，编辑链改了 message 也按它校。
> 依据 Conventional Commits 1.0.0，加上本仓库的中文写法约定。

---

## 一、结构

```text
type(scope): 中文描述

- 动词开头的一条变更
- 动词开头的一条变更

Closes #123
```

三段之间各空一行。scope 可省；footer 按需。

---

## 二、type 怎么选

| type | 含义 | 该用 | 不该用 |
|---|---|---|---|
| `feat` | 新增用户可感知的能力 | 加了新行为、新接口、新命令 | 内部结构调整、只改文档 |
| `fix` | 修复错误行为 | 修 bug、修错误输出、修边界 | 新功能自带的小调整（那属于 feat） |
| `refactor` | 不改外部行为的重构 | 拆函数、改结构、去重 | 顺手改了行为还叫重构 |
| `perf` | 性能优化 | 有可量化的快/省 | 没测过的「感觉更快」 |
| `docs` | 只动文档 | README、注释、说明 | 文档 + 代码混在一次 |
| `test` | 只动测试 | 补用例、修夹具 | 为了让测试过而改业务代码 |
| `chore` | 配置、依赖、杂项维护 | 版本号、忽略规则、脚本参数 | 有业务行为的改动 |
| `build` | 构建系统与打包 | 构建配置、依赖锁定 | 业务代码 |
| `ci` | 流水线配置 | workflow、hook 配置 | 本地脚本 |
| `revert` | 回滚既有提交 | 撤回某次提交 | 手工反向改一遍 |

仓库已有习惯优先于本表：`git log --oneline -20` 看一眼别人怎么写。

---

## 三、scope 怎么定

- 优先用**仓库里已经出现过的 scope**；没有先例时，用改动最集中的一级目录或模块名。
- 跨多个模块且无法归到一个名字时，省掉 scope，别硬凑。
- 不用 `misc`、`core`、`common`、`update` 这类没有信息量的词。
- 中文还是英文跟仓库既有习惯走；新仓库默认用目录名。

---

## 四、描述（冒号后那半句）

| 规则 | 说明 |
|---|---|
| 中文 | 标题正文都中文，`type` 与 `scope` 保持原样不翻译 |
| 动词开头 | 新增 / 修复 / 重构 / 优化 / 更新 / 调整 / 删除 / 补全 / 回滚 / 拆分 |
| ≤ 20 个汉字 | 超了说明塞了两件事 |
| 不加句号 | 标题不是句子 |
| 不说空话 | 「优化代码」「修改问题」等于没写，要写具体做了什么 |
| 不出现「和」「并」「顺便」 | 出现就是该拆成两次提交的信号 |

---

## 五、正文

- 每条 bullet **动词开头**，一条一个事实。
- 简单改动 1–2 条，常规改动 3–6 条；为凑条数硬写反而稀释信息。
- 讲**行为、影响、验证**，不讲文件路径。文件本身是交付物时才列。
- 最后一条常写验证方式（跑了什么检查、结果如何）。
- 正文超过 6 条还讲不清 → 回到生成链 Step 3 重判边界。

---

## 六、破坏性变更

两种等价写法，选一种：

```text
feat(api)!: 时间戳字段改为 ISO-8601 字符串

- 影响所有解析时间字段的调用方
```

```text
feat(api): 时间戳字段改为 ISO-8601 字符串

BREAKING CHANGE: createdAt 由数字改为 ISO-8601 字符串，按数字解析的客户端需要同步修改。
```

规则：

- footer 的 token 必须大写 `BREAKING CHANGE`。
- 必须写清**谁受影响、要改什么**，不能只写「不兼容」。
- 破坏性变更可以出现在任何 type 上，不只是 feat。

---

## 七、footer

| 写法 | 用途 |
|---|---|
| `Closes #123` / `Fixes #123` | 合并后自动关闭 issue |
| `Refs #123` | 仅关联，不关闭 |
| `Co-authored-by: 名字 <邮箱>` | 共同作者 |

footer 与正文之间空一行，每行一个 token。

---

## 八、反例对照

| 反例 | 问题 | 改成 |
|---|---|---|
| `update code` | 无 type、无信息 | `refactor(api): 抽出错误映射` |
| `fix: 修复了登录问题。` | 过去时、句号、问题模糊 | `fix(auth): 拒绝已过期的访问令牌` |
| `feat: 新增导出接口并修复登录并更新文档` | 一次提交三件事 | 拆成 feat / fix / docs 三次 |
| `chore: 一些杂项` | 空洞，等于什么都没说 | `chore(gitignore): 忽略本地构建产物` |
| `feat: 优化了查询性能` | 性能该用 perf，且没给验证 | `perf(query): 批量预取改为单次查询` |
| 正文列 20 个文件名 | 罗列而非描述行为 | 改写成「改了什么行为、影响什么」 |

---

## 九、写完自检四问

1. 只读标题，能知道改了什么吗？
2. 标题里有「和 / 并 / 顺便」吗？有就拆。
3. 正文有哪条是在罗列文件名而不是讲行为？
4. 不了解上下文的人看完，能判断影响范围吗？

四问都过再提交。一条都答不上来时，问题通常不在措辞，而在边界没定清。
