# Write Knowledge Doc

把一类用户还不懂的技术知识整理成一篇条目式知识文档。产出的文档要同时服务两个读者：人（快速理解一个陌生概念）和 AI（检索时拿到准确、自包含的答案）。判据是自包含性——读者只读这一篇，能否独立理解这个概念。

## 适用边界与两种模式

**模式判定在阶段 1 完成**：知识点是「一个概念」还是「一个多主题的领域」？

- **模式一 · 条目式（默认）**：适用零散知识点。一篇一个概念，多篇陆续积累，彼此没有内在顺序。五章固定骨架，H2 用阿拉伯数字编号 `1.`~`5.`。
- **模式二 · 成体系式（用户明确要求时）**：适用调研报告、领域综述、多主题成体系文档。章节数由内容决定，H2 用中文数字编号 `一、二、三`，H3 用 `x.y` 编号。触发词：调研报告、成体系文档、领域综述、多章节长文档。
- 用户没明说时按模式一处理；用户的要求横跨两种模式（「把调研结果整理成一篇能查的文档」）时，先说明两种模式的差别再确认。

**不适用**：教程、操作手册、API 参考这类「照着做」的文档，以及有目录树的产品文档体系。

## 工作流总览

五个阶段，阶段之间有两处硬性关口：**骨架必须经用户确认后才填充**，**填充稿必须经读者测试通过后才入库**。不要一次性吐出全文。

```
定篇边界 → 搭骨架（交用户确认）→ 逐节填充 → 排版与反模式自检 → 入库与读者测试
```

## 阶段 1：定篇边界

1. 知识点由用户指定；AI 负责判断这一篇该讲到什么边界。
2. 判据只有一个：**读者只读这一篇，能否独立理解这个概念**。能，边界就是对的。
3. 原则是「只讲一件事，但要把这件事讲完整」——拆分是为了让链接指向明确，不是让内容变浅。拆太宽会让链接含义被污染，拆太碎会切断链接网络，两者只有权衡、没有精确判据。
4. 边界拿不准（知识点明显该拆两篇、或与已有条目重叠）时，把两种划法和各自代价摆给用户选，不要自作主张合并或拆分。

## 阶段 2：搭骨架并交用户确认（硬性）

按 [references/entry-template.md](references/entry-template.md) 生成骨架交给用户：

- frontmatter 六字段：`title`、`status`、`created`、`updated`、`tags`、`verified`（字段规则见阶段 3）。
- 五个章节标题，**编号与文字都是固定契约，不得改写、不得省略编号、不得调整顺序**：
  `1. 它解决什么问题`、`2. 它怎么解决的`、`3. 一个具体场景`、`4. 边界与例外`、`5. 相关概念`。
- 每节下面只写 1-2 行要点提示，标出该节要回答的具体问题。
- **用户确认前不进入填充**。五章固定，只能在尾部按需追加章节（追加章节从 `6.` 开始接续编号，见模板）。无法与用户交互时（无人值守执行），把完整骨架列进交付说明供用户事后审阅，再直接进入填充。
- 骨架阶段的 `status` 和 `verified` 是占位值：填充完成后必须回填为真实判断（见阶段 3）。

## 阶段 3：逐节填充

### frontmatter 规则

| 字段 | 规则 |
|---|---|
| `title` | 必须是概念本身。来源导向的标题（「某文章读书笔记」「某次故障复盘」）是反模式。 |
| `status` | 封闭三取值：`seedling`（粗糙早期，只有原始问题和转述）、`budding`（已用自己的话重写，可以链接）、`evergreen`（概念自洽，人和 AI 都能直接复用）。半成品也入库，用 status 区分成熟度，不要等完美才保存。 |
| `verified` | 封闭三取值：`all`（每条结论都查过来源）、`partial`（部分查过）、`none`（全部未查）。AI 整理的文档必须写这个字段——没有它，读者只能默认全部未经验证。 |
| `created` / `updated` | `YYYY-MM-DD`，每次修订更新 `updated`。 |
| `tags` | 与正文术语一致，同一概念全文一个名字。 |

**事实纪律**：每条事实标注来源——出处二选一：全部集中放「它怎么解决的」末尾的来源表（覆盖全文，含其他章节的事实），或就地括注。同一出处不要两处都写。不新增来源没有提供的数字、日期、时限、能力、条件——AI 改写最容易在总结句里丢掉限定条件（「通常」变成「一定」、「某版本之前」变成「现在」）。查不到的写进核实状态，不要用「一般认为」模糊带过。

### 五个章节怎么写

1. **它解决什么问题**（放在主位，章节标题 `1. 它解决什么问题`）。这是理解的核心：先定义问题，**尽量不要提到你要定义的这个术语**。用术语解释术语是同义反复，等于没解释。写完自查：遮住这一节的概念名通读一遍，读者是否仍知道「它在解决什么麻烦」。
2. **它怎么解决的**（`2. 它怎么解决的`）。概念如何回应上面的问题——关键机制、组成、工作方式。精确值（参数名、错误码、默认值、版本号）用表格，不用段落。
3. **一个具体场景**（`3. 一个具体场景`）。贯穿全篇的真实例子：一段请求响应、一条命令及其输出、一段配置或日志。AI 整理的内容最缺这个；只给抽象描述不给例子是反模式。示例要最小但完整，讲清「输入是什么、发生了什么、输出是什么」。
4. **边界与例外**（`4. 边界与例外`）。具体的不适用场景和触发条件（「当 X 为 Y 时不适用」），不是「仅供参考」式的免责声明。已知没查证的部分也写在这里。
5. **相关概念**（`5. 相关概念`）。每条链接写明**为什么这篇相关**——「X 是 Y 的上位概念，这篇讲的是……」这样的关系说明。不写理由的链接只是养成浅薄的习惯；对 AI 而言，链接理由是检索时唯一能拿到的关系信号。

### 导语（第一个 ## 之前，无标题）

- 首句是一句话定义，且**标题作主语**（「渐进披露是……」而不是「渐进披露（progressive disclosure）……」）。
- 首句之后接三行，直接标注 frontmatter 字段名，让读者能把正文中文与 frontmatter 英文值对应起来：
  - 适用场景：什么时候该查这篇。
  - 成熟度（status: <值>）：当前成长阶段，一句话说明。
  - 核实状态（verified: <值>）：哪些结论查过来源、哪些没有。
- 为什么写进正文而不是只写 YAML 注释：知识库渲染 frontmatter 时不显示注释，只写注释的条目入库后在库里仍然看不懂这两个字段。注释写给生成者，正文行写给读者。
- 导语里的重要信息，正文必须有覆盖。

### 写作语气

先接住读者再往下解释；术语首次出现时就地解释一次，之后全文用同一字符串；比喻只在「为什么」语境出现一次，其后立即给字面定义；不用感叹号，不夸大。

## 阶段 4：排版与反模式自检

排版硬规则（完整速查见 [references/typography.md](references/typography.md)）：

1. **结论前置**：79% 的读者是扫描式阅读，前两段必须给答案。这也是 AI 省 token 的唯一一致诉求。
2. **能用表格就不用图文混排**：表格既是人最好的扫描格式，也是 AI 最易解析的结构。
3. **图文分工**：图回答「长什么样」（空间结构、连接关系、时序），文字回答「是什么/为什么」，表格回答「有哪些/是多少」，代码回答「照做就行」。用 Mermaid——它是文本协议，人和 AI 各取所需；拿不准图型时选更抽象的那个（flowchart 画时序只损失顺序信息，时序图画流程会污染交互语义）。
4. **关键信息留在文本里**：截图承载逻辑对 AI 完全不可读（无法 diff、无法检索）。用了渲染图必须保留源码。
5. 一段一个论点；每段加粗最多 2-3 处。正文行宽 50-75 字符是推荐值，**100 字符是自检脚本的红线**，超过必须拆行。

写之前先过一遍反面模式（完整清单见 [references/anti-patterns.md](references/anti-patterns.md)），高频四条：一篇混多种目的、只描述不给例子、没有相关链接、同一概念多个名字。

## 阶段 5：入库与读者测试（硬性）

### 入库

- 条目平铺，不建主题树；顶层只有一个入口页。不要一开始分「网络类」「数据库类」。
- 文件名（slug）一经确定不改；要改标题改文档内 H1。改了 slug，所有指向它的链接都会断。
- 新建条目只做两件事：写完，加链接（含理由）。不问「该归到哪一类」。知识库为空时首条目可以暂时不链接，等宿主条目或 MOC 出现后补上——链向一个只有标题的条目也是允许的。
- MOC 按需诞生：某个概念域的链接多到通读不动了，才为它写一篇 MOC。

### 读者测试

用一个**无上下文的 AI 实例**，只喂这篇文档和读者会问的问题，看它能否答对。具体操作见 [references/reader-testing.md](references/reader-testing.md)。这一步同时验证两个读者：无上下文的 AI 能读懂，说明自包含性合格；人读得顺，说明它对人也可读。测试不通过就回到阶段 3 改，不要直接入库。

无法新建会话时（单会话一次跑完整个工作流、上下文已被自己污染）按 reader-testing.md 的降级方案执行：优先开子 agent 或让用户手动开新会话，最弱方案是遮住上下文自答模拟——无论哪种降级，都必须在交付说明里如实标注验证强度。

### 条目自检

交付前运行（路径是插件安装目录下的绝对路径，从其他工作目录执行时不要照抄相对路径）：

```bash
python3 <skill 安装目录>/scripts/validate_knowledge_entry.py <条目文件>
```

脚本检查 frontmatter 六字段与枚举取值、五个核心章节的编号与顺序（1-5 按序、编号不得省略）、导语首句、导语的成熟度与核实状态标注行、来源导向标题、「问题」章节是否泄漏概念名、例子与链接是否齐备。**全部 error 清零才算交付**；warning 逐条处理或说明。

模式二的成体系文档同样跑自检：脚本按无 frontmatter 判定为模式二，检查 H1 存在与 H2 中文数字编号连续（一、二、三……）。

## 人机分工

| 环节 | 谁做 | 说明 |
|---|---|---|
| 选定知识点、判断该不该整理 | 用户 | AI 无法判断你对什么有困惑 |
| 收集材料、提取事实 | AI | 每条事实标注来源 |
| 判定「它解决什么问题」 | 用户审 | 理解的核心，AI 最容易写成同义反复 |
| 搭骨架、生成初稿 | AI | 按模板 |
| 逐节核对事实 | 用户 | 读者测试可直接复用 |
| 写链接理由 | 用户 | 不能外包——它决定链接是知识还是噪声 |
| 更新 status 和 verified | 用户 | 成熟度和可信度是你的判断 |

用户不在场时（无人值守执行），AI 可以代填上述判断，但取保守值：`status` 默认不高于 `budding`（结构完整且事实全部核实的条目除外，可标 `evergreen`），`verified` 不高于 `partial`，并在交付说明里列出待用户回填的项。

## 完成清单

- 篇边界经用户确认，判据（只读这篇能独立理解）成立。
- frontmatter 六字段齐全，status 和 verified 取值合法且如实。
- 五个核心章节齐全，编号 1-5 按序、文字与模板一致，未出现无编号或乱序章节。
- 导语三行齐备：适用场景、成熟度（status: 值）、核实状态（verified: 值）。
- 每个概念配了具体例子；相关概念每条链接写了理由（知识库为空时的首条目除外）。
- 反面模式清单已过；排版五条硬规则已过。
- 读者测试通过（无上下文 AI 实例能答对基本问题）。
- 自检脚本 error 清零。
- 入库路径平铺、slug 未与已有条目冲突。
