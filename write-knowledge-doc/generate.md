# 生成链

给定一个知识点，产出一篇能独立读懂的知识文档。五步，其中两步是硬门禁。

```
定边界 → 搭骨架（门禁：用户确认）→ 逐节填充 → 校验 → 验收与入库（门禁：理解链通过）
```

不要一次性吐出全文。每一步的产物是下一步的唯一输入；跳过一步或倒着走，都会在最后一步返工。

---

## Step 1 需求对齐

先定这六个维度。**能从上下文推断的直接采用，推断不出的才问，一轮问完，提问不超过 3 个。**

| 维度 | 为什么必须定 | 缺失时怎么办 |
|---|---|---|
| 知识点 | 决定这篇讲什么 | 不可默认，必须问 |
| 篇边界 | 决定拆不拆 | 先按「只讲一件事、但把这件事讲完整」推断；若含两个可独立成立的独立概念，或预估超过 300 行，把两种划法和各自代价摆给用户选 |
| 模式 `kind` | 决定编号体系 | 默认 `entry`；出现「调研报告 / 综述 / 成体系」才 `system` |
| 材料来源 | 决定 `verified` 与来源标注方式 | 无材料时按既有知识起草，`verified: none`，在交付说明里写明未核 |
| 读者与用途 | 决定术语密度和例子类型 | 默认「半年后的自己 + 检索型 AI」：术语首次出现即解释，例子要能复现 |
| 入库位置与同名条目 | 决定 slug 与是否需要合并 | 平铺，不建目录；同名条目已存在 → 先问是补充还是合并 |

**门禁**：知识点与篇边界没有明确答案时，**禁止进入 Step 2**。不许「先写起来再调整边界」——边界一改，五章内容全要重排。

**产物**：一段对齐结论（六项各一句），作为后续所有步骤的输入。

---

## Step 2 搭骨架

读 [references/skeleton.md](references/skeleton.md)（契约）与 [entry-template.md](references/entry-template.md)（可复制模板），产出骨架：

1. frontmatter 八字段齐全。`created`/`updated` 用当天日期；`status: seedling`、`verified: none`、`applies_to: unknown` 是**占位值**，填充后必须回填真实判断。
2. H1 与 `title` 一致。
3. 导语四行（适用场景 / 适用范围 / 成熟度 / 核实状态）先写占位句，替换掉模板里的说明文字。
4. 五个 H2 按契约写死；每节下面只写 **1–2 行要点提示**，标出这节要回答的具体问题，**不写正文**。
5. 需要追加章节时才追加，从 `6.` 起接续。

**门禁**：骨架必须交用户确认后才填充。一次性把整个骨架列出来，不要一节一问。无人值守时，把完整骨架写进交付说明供事后审阅，再继续填充。

骨架阶段不要跑内容校验——章节还没内容，报的都是预期内的 WARN。

---

## Step 3 逐节填充

按 1→5 顺序写，**每写完一节就地按判据自查**，不要攒到最后一起看。判据见 skeleton.md 的表格，写法细则与反例见 [writing-rules.md](references/writing-rules.md)。

高频错法，写的时候对着改：

| 节 | 最常见的错法 | 怎么改 |
|---|---|---|
| 1 | 用术语解释术语（「X 是一种解决 X 问题的机制」） | 换成没有这个概念的处境描述；写完遮住概念名读一遍 |
| 2 | 罗列特性，不回答「怎么回应第 1 节的麻烦」 | 每个机制后面补一句它消掉了哪个具体麻烦 |
| 3 | 抽象举例（「比如某个系统会……」） | 换成一次具体的请求/命令/日志，讲清输入、发生什么、输出 |
| 4 | 免责声明（「仅供参考」「具体以官方文档为准」） | 换成触发条件：「当 X 为 Y 时不适用」 |
| 5 | 堆一串裸链接 | 每条补「为什么相关」，写成一句关系判断 |

事实纪律（来源标注、限定条件、不新增数字）见 [writing-rules.md](references/writing-rules.md) 第一节。这一节是返工最集中的地方，**改写的每一步都会掉限定条件**。

---

## Step 4 校验

```bash
python3 <skill 目录>/scripts/validate_knowledge_doc.py <文档路径> --stage draft
```

路径按实际安装位置写，不要照抄相对路径。

- **ERROR 必须清零**才算可交付。每条 finding 都带 `fix`，按它改，不要绕过脚本改判据。
- **WARN 逐条处理**，或在交付说明里写清为什么不改。不接受「先放着」。
- `--json` 输出结构化结果，便于批量处理多篇。
- 校验之前把 `status`/`verified`/`applies_to` 回填成真实判断，不要留着 `seedling`/`none`/`unknown` 占位。`applies_to` 尤其容易漏：不填或填 `universal` 就等于宣称「这条结论永远成立」。

脚本抓不到的四类问题，人工对着 [anti-patterns.md](references/anti-patterns.md) 过一遍：一篇混多种目的（Kitchen Sink）、同一概念多个名字（术语漂移）、警告框泛滥、写显而易见的操作（UI 旁白）。

---

## Step 5 验收与入库

### 5.1 理解链验收

走 [understand.md](understand.md) 的问答协议，**不在这里重复定义**：把整篇文档给一个无上下文的实例，问 3–5 个问题，至少覆盖「概念是什么」「解决什么问题」「什么时候不适用」。

不通过 → 回到 Step 3 补对应章节，再重跑。**不要靠改问题凑通过**。

无法新建实例时按 [qa-protocol.md](references/qa-protocol.md) 的降级档执行，并在交付说明里标注验证强度。

### 5.2 入库

- 条目**平铺**，不建主题树，顶层只留一个入口页。不要一开始分「网络类」「数据库类」。
- 文件名（slug）一经确定不改；要改标题只改 `title` 与 H1。
- 新建条目只做两件事：写完，加链接（每条写明理由）。不问「该归到哪一类」。
- 首篇没有可链接对象时，按 skeleton.md §2.3 的豁免句写，不要留空。
- MOC 按需诞生：某个概念域的链接多到通读不动了，才为它写一篇。

### 5.3 结束

交付说明只写四件事：文件路径、`status`/`verified`/`applies_to` 的取值与依据、验收用了哪档、还有哪些待用户回填。

**到此结束。** 不做「顺手再优化一遍」，不重跑已通过的检查，不再改已经交付的内容。

## 人机分工

| 环节 | 谁做 | 说明 |
|---|---|---|
| 选定知识点、判断该不该整理 | 用户 | AI 无法判断你对什么有困惑 |
| 收集材料、提取事实 | AI | 每条事实标注来源 |
| 判定「它解决什么问题」 | 用户审 | 理解的核心，AI 最容易写成同义反复 |
| 搭骨架、生成初稿 | AI | 按契约 |
| 逐节核对事实 | 用户 | 可直接复用验收环节的问题 |
| 写链接理由 | 用户 | 不能外包——它决定链接是知识还是噪声 |
| 定 `status`、`verified` 与 `applies_to` | 用户 | 成熟度、可信度、适用范围都是人的判断 |

用户不在场时 AI 可代填，但取保守值：`status` 不高于 `budding`（结构完整且事实全部核实除外），`verified` 不高于 `partial`，并在交付说明里列出待回填项。
