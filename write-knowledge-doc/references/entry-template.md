# 条目模板（注释版）

阶段 2 搭骨架和阶段 3 逐节填充都从这里开始。左列是必须保留的结构，右列注释是该部分的规则出处。

```markdown
---
title: 概念名（标题必须是概念本身，不能是来源）
status: budding      # 成熟度三选一：seedling（粗糙早期）/ budding（已清理、可链接）/ evergreen（概念自洽）
created: 2026-10-13   # 实际使用当天日期，不要照抄模板日期
updated: 2026-10-13
tags: [分布式, 接口设计]   # 与正文术语一致；示例值照抄前先替换
verified: partial    # 核实状态三选一：all（每条都查过来源）/ partial（部分查过）/ none（全部未查）
---

（H1 概念名——与 title 一致）

概念名是……（一句话定义。标题作第一句主语；不要写成「概念名（英文名）是……」）

适用场景：什么时候该查这篇。

成熟度（status: budding）：已用自己的话重写、可以链接；概念尚未完全定稿。

核实状态（verified: partial）：部分结论查过来源，未查证的见「边界与例外」。

## 它解决什么问题

（先定义问题，尽量不要提到「概念名」这个术语。写完自查：遮住概念名通读一遍，读者是否仍知道它在解决什么麻烦。）

## 它怎么解决的

（概念如何回应上面的问题：关键机制、组成、工作方式。精确值用表格，不用段落。）

## 一个具体场景

（贯穿全篇的真实例子：一段请求响应、一条命令及其输出、一段配置或日志。讲清「输入是什么、发生了什么、输出是什么」。）

## 边界与例外

（具体的不适用场景和触发条件：「当 X 为 Y 时不适用」。已知没查证的部分写在这里。）

## 相关概念

- [[上位概念]] —— 为什么相关：这篇讲的是 X 的具体形态，那一篇讲 X 本身。
- [[并列概念]] —— 为什么相关：两者解决相邻问题，容易混。
```

## 按需追加的章节

五个核心章节之外，以下章节在内容真的需要时追加，不要预埋：

| 章节 | 什么时候加 |
|---|---|
| 常见疑问 | 同一问题被问到两次以上 |
| 延伸 | 有明确的深入路径（「要深入 X，读 Y」） |
| 术语表 | 概念涉及 5 个以上必须理解的术语 |
| 目录 | 篇幅超过 300 行时 |

## 与成体系文档的区别

条目式主干是「问题→解法→例子」五章。成体系产品文档的主干是「是什么/怎么运作/为什么」三章并列，外加教程与参考双轨。两者混用是 Kitchen Sink 反模式——本篇模板只服务零散知识点。
