# 骨架契约

> 编号、章节、字段的**唯一真相源**。`generate.md` 按它搭骨架，`edit.md` 按它判断结构是否合规，
> `scripts/validate_knowledge_doc.py` 按它做校验。其他文件只引用，不复述。
> 违反本文件的任何一条，校验脚本都会报 ERROR。

---

## 一、frontmatter（八字段）

| 字段 | 必填 | 取值 | 规则 |
|---|---|---|---|
| `title` | 是 | 字符串 | **必须是被定义的概念本身**。来源导向标题（「某文章读书笔记」「某次故障复盘」）是反模式 |
| `kind` | 是 | `entry` \| `system` | 决定编号体系。缺这个字段无法判断该用哪套编号 |
| `applies_to` | 是 | `universal` \| `unknown` \| 具体范围 | 结论对哪个版本、环境成立，见下方说明 |
| `status` | 是 | `seedling` \| `budding` \| `evergreen` | 成熟度，见下方定义 |
| `verified` | 是 | `all` \| `partial` \| `none` | 核实状态，见下方定义 |
| `created` | 是 | `YYYY-MM-DD` | 建篇日期，此后不变 |
| `updated` | 是 | `YYYY-MM-DD` | 每次修订更新。**必须 ≥ `created`** |
| `tags` | 是 | `[a, b]` 内联列表 | 与正文术语一致；同一概念全文一个名字 |

**applies_to 三选一**（必填，不填就等于默认「对当前版本永远成立」，那是最危险的默认值）：

| 取值 | 含义 | 例子 |
|---|---|---|
| `universal` | 概念性结论，不随版本或环境变化 | 「幂等指同一操作执行多次的最终影响与一次相同」 |
| 具体范围 | 结论只在某个版本、产品、平台或配置下成立 | `MySQL 8.0+`、`Kubernetes ≥ 1.26`、`JDK 17`、`仅 Linux cgroup v2` |
| `unknown` | 尚未确认边界 | 写 `unknown`，并在「4. 边界与例外」写明哪部分未确认 |

范围写**可比对的值**：版本号、产品名、平台、配置项。不写「最新版」「常见版本」「一般来说」——这些词无法判断是否命中。

**status 三档**（半成品也入库，不要等完美才保存）：

| 值 | 含义 | 判据 |
|---|---|---|
| `seedling` | 粗糙早期 | 只有原始问题和转述，没有自己的组织 |
| `budding` | 可以链接 | 已用自己的话重写，结构完整，但概念尚未定稿 |
| `evergreen` | 可直接复用 | 概念自洽，人和 AI 都能当作结论引用 |

**verified 三档**（AI 整理的文档必须写这个字段，否则读者只能默认全部未经验证）：

| 值 | 含义 |
|---|---|
| `all` | 每条结论都查过来源 |
| `partial` | 部分查过，未查的在「4. 边界与例外」里点明 |
| `none` | 全部未查 |

## 二、entry 模式的五章

编号与文字都是**固定契约**：不得改写文字、不得省略编号、不得换成中文数字、不得调整顺序。

| 编号 | 标题（逐字固定） | 要回答的问题 | 过关判据 |
|---|---|---|---|
| 1 | `1. 它解决什么问题` | 没有这个概念的处境有什么麻烦 | 遮住概念名通读这一节，读者仍知道在解决什么麻烦 |
| 2 | `2. 它怎么解决的` | 概念如何回应上面的问题：机制、组成、工作方式 | 每个机制都能对上第 1 节提出的某个麻烦 |
| 3 | `3. 一个具体场景` | 一次真实的输入、过程、输出 | 三段齐全且可复现；不是「比如某个系统会……」 |
| 4 | `4. 边界与例外` | 什么条件下不适用、哪些结论没查证 | 每条带触发条件「当 X 为 Y 时不适用」，不是免责声明 |
| 5 | `5. 相关概念` | 相邻概念是什么关系 | 每条链接写明为什么相关；裸链接堆砌不合格 |

### 2.1 追加章节

五章之外的内容**一律放在五章之后，从 `6.` 起接续编号**，不得预埋、不得插在五章中间、不得断号。

| 编号 | 章节 | 什么时候加 |
|---|---|---|
| 6 | 常见疑问 | 同一问题被问到两次以上 |
| 7 | 延伸 | 有明确的深入路径（「要深入 X，读 Y」） |
| 8 | 术语表 | 概念涉及 5 个以上必须理解的术语 |

除五章与上述追加章节外，**不允许出现其他 H2**。想加就得先给它一个编号，编号断了就是格式漂移。

### 2.2 H3 规则

- H3 可不用；**一旦使用，必须带 `x.y` 编号**，`x` 等于父章编号（第 2 章下只能是 `2.1`、`2.2`）。
- H3 不承担结构契约，只做章节内部的自然分段，编号连续即可。

### 2.3 首条目豁免

知识库为空时，第一篇没有可链接的对象。`5. 相关概念` 允许且**仅允许**写这一句：

```
暂无。本条目为知识库首篇，出现相关条目后回填。
```

其他章节不适用本豁免——空章节一律 ERROR。

## 三、system 模式

| 项 | 规则 |
|---|---|
| H1 | 有且仅有一个，等于 `title` |
| H2 | 中文数字编号 `一、` `二、` `三、`，**连续、不跳号、至少 2 个** |
| H3 | `x.y` 编号，`x` 等于父章的中文序号对应的阿拉伯数字（第一章下是 `1.1`） |
| 导语 | H1 与第一个 H2 之间有一段，说明定位、覆盖范围、结构总览 |
| 章节数与顺序 | 由内容决定，不套五章骨架 |
| frontmatter | 与 entry 相同八字段，`kind: system` |

**两种模式不得混用**：entry 里不得出现中文数字编号的 H2，system 里不得套五章骨架。编号体系是模式的身份标识，混用即格式漂移。

## 四、迁移：旧条目（0.1.2 之前）

旧条目没有 `kind` 与 `applies_to` 字段，会被校验脚本判为 ERROR。各补一行即可：

```yaml
kind: entry          # 条目式；成体系文档写 system
applies_to: universal   # 不随版本变化；有版本依赖就写具体范围，不确定写 unknown
```

旧条目曾允许「无 frontmatter 即成体系」，该隐式规则已取消：**没有 frontmatter 一律视为结构缺失**，因为「忘写」和「故意不写」在结果上无法区分，而前者是错误、后者是设计缺陷。
