# 反面模式

写之前扫一遍。左列是症状，右列是改法；标了码的能被校验脚本抓到，其余必须人工过。

---

## 一、内容层

| 反面模式 | 症状 | 改法 | 脚本 |
|---|---|---|---|
| 用概念解释概念 | 「X 是一种解决 X 问题的机制」 | 改写成没有 X 时的具体处境 | 部分（`PROB-LEAK`） |
| 只描述不给例子 | 四段抽象描述，没有一个输入输出 | 补一次真实的请求/命令/日志 | `SCENE-NOEXAMPLE` |
| 免责声明冒充边界 | 「仅供参考」「具体以官方文档为准」 | 换成触发条件「当 X 为 Y 时不适用」 | 无 |
| 无理由链接 | 文末堆一串相关条目 | 每条写明属于哪种关系：上下位/并列/因果/替代 | `REL-BARE` |
| 死胡同 | 没有相关条目、没有下一步 | 补链接与理由；首篇用豁免句 | `REL-DEADEND` |
| 术语漂移 | 一段叫 workspace，一段叫 project | 一个概念一个名字，全文同一字符串 | 无 |
| 来源导向标题 | 「某文章读书笔记」「某次故障复盘」 | 标题必须是概念本身 | `TITLE-SOURCE` |
| 限定条件蒸发 | 原文「某版本之前不支持」写成「不支持」 | 回头搜原文的「通常/某版本/仅当」，逐个确认还在 | 无 |
| 编造补充 | 为了话说圆，加一句「一般来说」 | 查不到就写查不到，降 `verified` | 无 |
| 范围含糊 | `applies_to` 写「最新版」「常见版本」「一般来说」 | 改成可比对的版本号/环境，或写 `unknown` 并在第 4 章说明；无法比对的范围等于没写 | 无 |

## 二、结构层

| 反面模式 | 症状 | 改法 | 脚本 |
|---|---|---|---|
| 编号缺失 | 五章写成无编号的 `## 它解决什么问题` | 编号 1–5 是固定契约 | `SEC-NUM` |
| 编号漂移 | 中英编号混用（`1.` 与 `一、` 并存） | 编号体系跟着 `kind` 走 | `SEC-NUM` / `SYS-H2-NUM` |
| 追加章节断号 | 五章后直接跳到 `7.`，或写成无编号的 `## 常见疑问` | 从 `6.` 接续，连续不跳号 | `SEC-GAP` / `SEC-EXTRA` |
| 模式混用 | 条目里塞中文数字大章，成体系里套五章 | 两种模式各管各的 | `SEC-*` / `SYS-*` |
| 省略 frontmatter | 「反正是内部文档」 | 没有 frontmatter 一律视为结构缺失 | `FM-MISSING` |
| 空章节 | 标题在、内容空 | 填上，或删掉该节（五章除外） | `SEC-EMPTY` |
| 导语缩水 | 只有一句话定义，缺适用范围、成熟度、核实状态行 | 四行齐备，含字段名 | `LEAD-APPLIES` / `LEAD-STATUS` / `LEAD-VERIFIED` |

## 三、目的层（脚本抓不到，必须人工判断）

| 反面模式 | 症状 | 改法 |
|---|---|---|
| Kitchen Sink | 一篇里混概念解释、教程、排错、API 参考 | 一篇只答一个目的；其余拆出去 |
| 警告框泛滥 | 每隔两段一个提示块 | 每篇最多 1–2 个 |
| UI 旁白 | 「要部署，点部署按钮」 | 不写显而易见的操作 |
| 目录膨胀 | 300 行的条目还加目录 | 条目是短文档，不加目录；超长就拆篇 |
| 等完美才入库 | 改十遍还不保存 | 半成品入库，用 `status` 标成熟度 |
| 一开始建主题树 | 先花两天设计目录结构 | 只写条目和链接，让结构自己长 |

---

## 四、脚本覆盖范围

`scripts/validate_knowledge_doc.py` 负责结构、编号、字段、可机读的内容信号（例子、链接、加粗、行宽）。它**不判断**内容对不对、边界写得够不够具体、链接理由是否成立——这四类只能人工过。

不要因为脚本通过就认为文档合格。脚本是门禁，不是审稿人。
