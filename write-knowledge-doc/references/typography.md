# 排版速查

## 双读者调和表

工业界没有「给人看的文档」和「给 AI 看的文档」两套写法。同一套 Markdown 用「渐进披露 + 结构化 + 自包含」分层服务两个读者。

| 维度 | 人需要 | AI 需要 | 调和方式 |
|---|---|---|---|
| 入口 | 目录、导航 | 判断「跟我手上的任务相关吗」 | 导语两行 scope 声明（适用场景 + 核实状态），替代泛泛引言 |
| 结论位置 | 常放最后（叙事） | 前置（省 token） | 首句给定义，导语给适用场景。人扫一眼，AI 少读 |
| 术语 | 首次出现时解释 | 一致、可精确匹配 | 就地解释一次，之后全文同一字符串 |
| 图表 | 渲染后的图 | 图的结构化语义 | Mermaid 是文本协议，人和 AI 各取所需 |
| 示例 | 最小、可运行 | 完整、含边界 | 一个最小示例 + 边界与例外章节兜住 |
| 篇幅 | 可接受长文 | 500 行/5000 token 上限 | 单篇控制在 300 行内，超出考虑拆篇 |
| 冗余 | 强调是噪声 | 多写一遍是保险 | 定义一次 + 交叉引用；关键约束用速查表汇总 |
| 指代 | 「该配置」读得顺 | 指代消解易错 | 每节首次用全名，跨节引用带章节名 |
| 比喻 | 降低门槛 | 歧义源 | 比喻只在「为什么」语境出现一次，其后立即给字面定义 |

三条最重要的调和原则：

1. **结论前置，论证后置**——唯一一条两个读者诉求完全一致的做法。
2. **表格是双读者的桥梁**——能用表格就不用图文混排。
3. **关键信息必须留在文本里**——截图承载逻辑对 AI 完全不可读。Mermaid 源码本身就是文本；用了渲染图必须保留源码。

## 图文分工判定表

| 内容特征 | 该用什么 | 判定标准 |
|---|---|---|
| 空间结构、连接关系（调用链、数据流向、依赖） | 图（flowchart/erDiagram/classDiagram） | 用文字描述需要 3 个以上「→」或「包含」才讲清 |
| 时间顺序、交互过程（请求响应、状态流转） | 图（sequenceDiagram/stateDiagram） | 涉及 2 个以上参与方，或有明确先后 |
| 抽象概念的解释与意图（为什么这样设计） | 文字 | 「为什么」「权衡」类问题 |
| 精确值（参数名、错误码、默认值、版本号） | 文字（表格优先） | 需要可复制、可搜索、可 diff |
| 操作步骤 | 文字（编号列表） | 读者要照着敲 |

一句口诀：**图回答「长什么样」，文字回答「是什么/为什么」，表格回答「有哪些/是多少」，代码回答「照做就行」。**

## Mermaid 图型选择

| 图型 | 适合 | 不适合 |
|---|---|---|
| flowchart | 分支判断、处理流程、决策树 | 有严格时序的多方交互 |
| sequenceDiagram | 调用时序、握手、同步异步差异 | 静态结构、数据模型 |
| stateDiagram | 有限状态机、生命周期、合法迁移 | 非状态型过程 |
| erDiagram | 实体关系、基数、主外键 | 请求时序、权限逻辑 |
| classDiagram | 继承组合聚合、接口契约 | 时序行为、部署拓扑 |
| mindmap | 概念总览、术语索引、知识地图 | 有条件分支的流程 |

**选型速判**：多方且有先后 → sequence；单方且有条件分支 → flowchart；只有状态没有先后 → state；只有实体和基数 → er；只有静态归属 → class；只有分类层级 → mindmap。

拿不准时**选更抽象的那个**：用 flowchart 画时序只损失顺序信息，用时序图画流程会污染「交互」语义，读者要在错误的心智模型上重建认知。

## 其他排版参数

- 正文行宽 50-75 字符（66 是常引用的甜蜜点）是**推荐值**；**100 字符是自检脚本的红线**，超过 100 必须拆行。中文混合文档以红线为准
- 代码块可略宽但设上限 80-100
- 加粗每段最多 2-3 处，只标术语、参数名、可点击值、危险项。加粗通胀后信号失效
- 用留白和接近性分组，不要靠分隔线堆叠
- 渐进披露两级封顶：超过两级折叠可用性显著下降
- 每小节独立回答一个问题，不依赖上一节的「该方法」「如前所述」——切块自包含
- 正文小节标题用「为什么需要重试」而不是「重试」：标题是人和向量模型共用的最强路由信号。条目模板的五个固定章节名与编号（`1.`~`5.`）除外——它们是固定契约，文字不改写、编号不省略、顺序不调整
