# 写作规则

> `generate.md` Step 3 逐节填充时读，`edit.md` 改内容时读。只讲怎么写，不讲结构（结构见 skeleton.md）。

结构与编号见 [skeleton.md](skeleton.md)，这里只说「怎么下笔」。每条规则后面跟一个反例——反例比正例更有用，因为要防的是具体的错法。

---

## 一、事实纪律

这是 AI 整理知识最容易失守的地方，四条都按硬要求执行。

### 1.1 每条事实标来源，二选一，不重复

- **集中式**：在第 2 章末尾放一张来源表，覆盖全文（含其他章节）的事实。
- **就地式**：在事实后面括注出处。

同一出处不要两处都写。选了哪种，全篇统一。

### 1.2 限定条件原样保留

改写时最容易掉的不是主句，是状语。以下三类必须逐字带过去：

| 类型 | 原文 | 常见的错改 |
|---|---|---|
| 频率 | 「通常需要 3 次重试」 | 「需要 3 次重试」 |
| 版本 | 「2.4 之前不支持」 | 「不支持」 |
| 条件 | 「在开启分区时才有此限制」 | 整句条件消失 |

**改写完回头搜一遍原文的「通常 / 一般 / 某版本 / 在…情况下 / 仅当」**，逐个确认它们在改写稿里还在。

版本类限定要升格成字段：如果整篇结论都依赖某个版本（「8.0 之后才默认开启」），把它写进 `applies_to` 与导语的适用范围行，而不是只写在某一节里——只写在一节的限定，检索时拿不到。

### 1.3 不新增来源没有的内容

不新增数字、日期、时限、能力、条件。想把话说圆而补的那句「一般来说」，通常就是编造的开始。

### 1.4 查不到就写查不到

写进 `verified` 与「4. 边界与例外」，明确说「此处未查证」。不要用「一般认为」「业界普遍」这类措辞把它盖住——那会让读者误以为有出处。

## 二、导语四行

导语是 H1 与第一个 H2 之间的正文，无标题。结构固定：**一句话定义 + 四行标注**。

```markdown
概念名是……（一句话定义，标题作主语）

适用场景：什么时候该查这篇。

适用范围（applies_to: MySQL 8.0+）：结论对哪个版本或环境成立。

成熟度（status: budding）：已用自己的话重写、可以链接；概念尚未完全定稿。

核实状态（verified: partial）：部分结论查过来源，未查证的见「边界与例外」。
```

- 首句**标题作主语**：「幂等是指……」而不是「幂等（idempotency）是指……」。
- 四行里直接写出 frontmatter 的字段名与取值。原因：知识库渲染 frontmatter 时**不显示 YAML 注释**，只写注释的条目入库后，读者看不懂这些字段。
- **适用场景与适用范围不是一回事**：前者答「什么时候该查」，后者答「结论在哪个版本/环境成立」。写「排查数据库压力时」是场景；写「MySQL 8.0+」是范围。
- 范围行写可比对的值。反例：「适用范围（applies_to: 最新版）」——「最新版」三个月后就不成立，而条目不会自动改。
- 注释写给生成者，正文行写给读者——两者都要有。
- 导语里承诺的信息，正文必须有对应内容。

## 三、语气

| 要求 | 反例 |
|---|---|
| 先接住读者再解释：第一句回答「这是什么」，不铺垫背景 | 「随着分布式系统的普及，幂等这个概念越来越重要……」 |
| 术语首次出现就地解释一次，之后全文用同一字符串 | 一段叫 workspace，下一段叫 project |
| 比喻只在「为什么」语境出现一次，随后立即给字面定义 | 通篇用「快递单号」类比，读者最后仍不知道幂等键存在哪 |
| 不用感叹号，不夸大，不用「极大地」「显著提升」这类空量词 | 「性能得到极大提升」 |
| 一段一个论点；加粗每段最多 2–3 处，只标术语、参数名、危险项 | 一段里五处加粗，等于没有重点 |

## 四、各章怎么写

判据在 [skeleton.md](skeleton.md) 的表格里，这里给下笔手法。

### 4.1 它解决什么问题

先描述**没有这个概念时的处境**，不要先给定义。

- 手法：写一个具体的麻烦现场——谁在什么时刻、因为缺了什么、做了什么错误决定。
- 自检：遮住概念名通读这一节，读者仍知道在解决什么麻烦。
- 反例：「幂等是一种解决重复执行问题的机制。」——用概念解释概念，读者读两遍仍不知道重复执行会怎样。

### 4.2 它怎么解决的

每个机制后面补一句它消掉了第 1 节的哪个麻烦。机制与麻烦要对得上号。

- 精确值（参数名、错误码、默认值、版本号）**进表格**，不进段落——段落里的数字不可检索。
- 反例：上来列「三大特性：原子性、一致性、持久性」。特性列表回答不了「它怎么回应上面的问题」。

### 4.3 一个具体场景

一次真实的输入、过程、输出。**最小但完整**：小到能一眼看完，完整到能自己复现。

- 可选形态：一段请求与响应、一条命令及其输出、一段配置、一段日志、一张时序图。
- 反例：「比如某个电商系统在支付时会用幂等键。」——没有输入、没有过程、没有输出，读者仍不知道怎么写。
- 图只在「长什么样」时说清问题才用；图里的关键信息必须在文字里也有一份（截图对检索完全不可读）。

### 4.4 边界与例外

写触发条件，不写免责声明。

| 写法 | 例子 |
|---|---|
| 对 | 「创建类操作天然不幂等：每次 `POST /orders` 都创建新订单，重复提交就是重复订单。」 |
| 错 | 「幂等并非万能，使用时需结合具体场景。」 |

已知没查证的部分也放这里，并明说是未查证。

### 4.5 相关概念

每条链接后面写一句**关系判断**，不是重复标题。

| 写法 | 例子 |
|---|---|
| 对 | `[[至少一次投递]]` —— 为什么相关：至少一次投递是幂等需求的主要来源，重复投递靠消费方的幂等处理消化。 |
| 错 | `[[至少一次投递]]` —— 为什么相关：相关概念。 |

关系有四种，选一种说清：上位/下位、并列易混、因果、替代方案。写不出属于哪种，说明这两篇其实不相关。

## 五、篇幅

- 单篇 **300 行是上限**，超过考虑拆篇，不加目录章节。
- 单节超过 60 行，先看是不是混进了第二个目的（Kitchen Sink）。
- 正文行宽 50–75 字符是推荐值，**100 字符是校验脚本的红线**。中文混合文档以红线为准。
