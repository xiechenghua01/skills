# 异步运行与后台可见性

入口：[SKILL.md](../SKILL.md)。派发异步子任务、使用 Agent Teams、等待后台 Job、暂停本轮或收尾时读取。以下事实于 2026-11-12 在 DSH 环境中核实；工具名、参数、必填项与返回结构以当前宿主 schema 为准，不从本文臆造参数。

## 1. DSH 原生子 agent

- 派发前先用 list_subagent_models 发现当前可用的 provider、model 与 reasoning_effort，再显式选择。不要硬编码历史别名或假设某个分组永远存在。
- 独立任务默认 fresh；subagent_fork 才继承已完成上下文。前置任务尚未完成、上下文不完整或包含无关材料时，用 fresh 并写清输入，不用 fork 假装继承。
- 派发前填写目标、输入、写入范围、依赖、验收与模型/执行器；实际 ID 只能在工具成功返回后登记，不预造 ID。格式见[角色与模型路由](model-routing.md)第 4 节。

## 2. Claude Code 与 Codex 外部执行器

- subagent_claude_code、subagent_codex 的参数只有任务 prompt、description 与 cwd；没有单次 model、timeout 或 resume。模型由插件实例或原生设置固定。
- 不要靠在 prompt 里写模型名来声称切换模型，也不要反复修改全局配置来切模型。需要不同模型时，使用能表达该选择的执行器，并记录实际值。
- 外部启动只返回子任务 ID；之后由完成通知返回最终文本或失败。不要把它当作本地子 Session。
- 外部实例没有本地子 Session，没有中间工具、思考、用量或进度流，不支持 send_message 续聊或 resume，也没有硬时限或副作用回滚。
- 外部任务要修复时，重新开一个任务，先读已有改动和现场，再带上必要上下文派发；不假装恢复原任务或原会话。
- 因为没有副作用回滚，派发时收窄写入范围，完成后必须读回实际改动；失败时先判断现场状态，再决定是否新开任务。

## 3. Agent Teams

- 用 list_agents 与 team_task_* 核对成员和任务状态；具体方法名与参数按当前 schema 读取。
- inactive 只表示当前没有轮次在跑，不是任务成功，也不代表成员不存在。
- list_agents 不是所有外部子任务的目录；不能据它断言某个外部子任务不存在或已结束。
- wait_agent 前先确认还有所需成员处于 running 或 provisioning；没有可等待的成员时不要空等。
- 对 inactive 成员用 send_message 启动前要有依据，例如已确认存在待办任务或明确分工；不凭猜测反复唤醒。
- Agent Teams 仍需收齐所有必需队友的结果才做最终交付，不能把“本轮结束”当作团队任务完成。

## 4. Bash 后台 Job

- 只有 bash 等后台 Job 使用 job_output 和 job_kill。
- 外部子任务 ID 不能当作 job_id 传给 Job 工具；两种身份和两种状态来源不能混用。

## 5. 等待纪律

- 普通异步子 agent 只剩等待时，遵循宿主规则结束本轮，让完成通知续轮；不忙轮询、不睡眠轮询、不占用主控空转。
- 不要为了保持 spinner 让主控反复检查或生成无进展的动作。
- 区分三个层次：
  - 本轮结束：当前回复暂停，后台任务可能仍在运行。
  - 子任务终止：运行时返回 completed、error、aborted 等终止结果；这不代表产物合格。
  - 整个交付完成：必需子任务结果已处理，实际产物已读回并整合，适用的必需审查与受影响验收已通过。
- 只有“本轮结束”时，用阶段状态说明后台任务；不能写成整个交付完成。

## 6. 后台不可见与阶段状态

本技能不创建 UI，也不承诺修复 DSH 的状态展示。DSH 自身界面等宿主能力才是实时视图；本技能发出的文字只是静态告知，不能代替常驻实时徽标。

外部子任务尚未结束、主控准备暂停本轮前，发一条简短阶段状态，必须包含任务名、已有实际 ID、仍在后台运行、尚未完成交付。不能只贴长 UUID，更不能写“全部完成”。示例：

> 阶段状态：修复设置页保存（子任务 ID：派发返回的实际 ID）仍在后台运行，尚未完成交付；本轮先结束，收到完成通知后继续整合与验收。

实际使用时把任务名与 ID 换成真实值；这段文字只说明当前已知状态。不要编造百分比、token 用量、当前工具、预计剩余时间或不存在的实时进度。计时很久没有进展不等于已经停止；无法确认状态时记为 unknown，不记为 completed。

## 7. 收尾核对

最终汇报前逐项核对：

- 逐个区分运行状态与终止结果：completed、error、aborted 等是运行时终止结果；pending、running、unknown 不是终止结果。后者存在于必需任务时，不能宣称交付完成；收到失败结果也不等于验收通过。
- 每个完成项的实际产物与改动已读回，不只信最终文本。
- 适用的必需独立审查已完成，问题有严重度、位置与依据或复现。
- 适用的必需测试、构建、类型检查与主控实机验收已执行并记录证据；可选未执行项与不适用项分别说明，不计入通过项，也不自动阻塞已约定范围交付。
- 仍在后台运行的任务列出任务名、实际 ID 与当前状态。
- 零运行数不等于成功；必需项没有执行、没有产物或证据不足时，明确写 pending、failed、unknown、blocked 或 not_run。

必需任务或适用的必需检查有遗漏、失败或证据不足时，不宣称交付完成；可选与不适用项遵循[验收协议](acceptance.md)。父 agent 停止不证明外部子 agent 已取消；没有停止接口时，不能谎称已停止，也不能直接启动替补同时写同一路径。若只能结束本轮，报告“本轮结束、任务仍在后台”，不要报告成子任务完成或整个交付完成。

## 8. 实时界面仍需单独实现

2026-11-12 的界面核查中，原生子 agent 条目有状态，Claude Code 外部条目仅标为“外部任务”；顶部后台 Job 的运行提示不能据此认定也覆盖了外部子任务。这是界面观察，不是该缺口已修复的证据，也没有完成父 agent 停止后的全流程回归。

如果另行开发状态展示，应复用宿主已有的外部任务目录与活动数据，先检查当前 Service、事件与 Slot 契约，不让技能额外维护一套状态。最低验收要求：主 agent 暂停后外部任务仍运行时持续可见；运行与失败、已终止、未知分开；`inactive` 和零运行数不直接显示为交付成功。技能的阶段消息不能替代这些界面验收。
