# 企业公开技能对比

Skill 开发闭环的差距与优化，是把上一版经验包的架构和写作原则，进一步转成可执行的开发、验证与交付机制。
原调研读取腾讯、阿里云、字节跳动公开技能及 Anthropic 评估工具源码，比较具体机制，而非按企业名气排名。
目标是：**用户已给清晰需求时，agent 可以推进开发、发现缺口、验证结果，而不重复访谈或只输出原则。**

适用范围（applies_to）：公开样本按下文版本固定；不承诺其他宿主支持相同接口或元数据。
成熟度（status: budding）：对比和执行协议已形成，尚未据此开发、安装并运行一个新的 skill。
核实状态（verified: partial）：机制来自静态原文/源码；未执行企业技能、连接云账号或运行模型对照评估。

## 一、先给判断：缺少的是可执行闭环，不是更多提示词

上一版经验包在短入口、职责分层、证据状态、精确写法、失败契约和测试方向上已经完整。
不能把这些已有内容说成完全缺失。与本次样本相比，主要差距是它们仍停留在模板和建议，
还没有形成一个 agent 可按结果推进的开发协议，也没有真实新 skill 的验证证据。

最值得补的六项：
1. 清晰需求直接执行，只有新增业务决策或未授权影响才停。
2. 需求、实现位置与验收用例能互相追踪。
3. 输入输出契约不只写在文档里，还能被代码和测试校验。
4. 工具结果、真实产物和完成状态相互核对，不相信自报完成。
5. 触发、任务执行、对照效果分开评估，不把一次显式调用当自动触发成功。
6. 环境、失败、恢复、安装和发布有明确边界；没有测到的范围不算支持。

原调研已新增执行协议和落地验收表，但没有把“文档已补充”说成“工程能力已验证”。

## 三、腾讯：学路由与回读，不照搬无条件重复确认

### 3.1 CloudBase CLI 的强项

CLI 技能不只写“部署云服务”，而是区分 CLI、MCP、应用内 SDK、数据库设计等不同路径。
先读 core，再按任务读领域参考；掌握当前流程与命令后明确停止加载：
原文 “Stop loading more context”，即**上下文足够时停止继续加载**。
这比“尽可能全面阅读资料”更适合 agent 精确执行。

它还区分国内/国际站与 `envId`，避免把环境错配误判为普通鉴权故障；
修改后通过 list/detail 回读，失败若干次后更换诊断路径，不一直重复相同命令。
这些是指令约定，未通过真实 CLI 和权限测试确认所有行为。

来源：[cloudbase-cli/SKILL.md](https://github.com/TencentCloudBase/skills/blob/930c3e4f75d3f3ae5ffd49fbd7ec216f344b6b66/skills/cloudbase-cli/SKILL.md)。

### 3.2 为什么不能照搬它的确认纪律

原文 “Always verify envId with the user”，即**总要向用户核实环境 ID**；
关联安全协议对非平凡改动再次要求明确确认，没有清晰授权后的豁免。
这对高风险云操作有保护作用，但不适合原样推广为每次本地 skill 开发都必须二次确认。

本包采用范围判断：用户已明确目标、对象、环境和允许动作，就继续；
只有新增影响、未授权覆盖/删除/发布或无法确定业务含义时，停下相关动作。
这不是降低安全标准，而是避免把已经获得的任务输入反复变成待审批问题。

来源：[变更安全协议](https://cnb.cool/tencent/cloud/cloudbase/CloudBase-AI-Toolkit/-/git/raw/main/config/source/skills/cloudbase-platform/references/protocols/change-safety-protocol.md)。

### 3.3 代码审查技能的价值与断层

它把确定性扫描与 LLM 语义审查分开，输出规则编号、严重性、文件和行号，便于程序消费。
但技能明确没有附带可执行脚本，原文 “No executable script is shipped”；
完整检查代码放在参考 README，用户同意后复制到临时文件运行。
这不是与交付脚本、测试绑定的同一种封装方式。

静态代码还发现规则清单与实现不一致：规则 PG-CR005 没有对应函数；
SEC001 声称覆盖 Dockerfile/compose，文件收集器却不包含这些格式；
大文件或读取失败返回空串，未显式报告未检查范围；warning 时退出码与 passed 定义也不一致。

可迁移的是“确定性检查 + 语义审查”；需要补强的是规则到检查函数的覆盖表、跳过报告和成功语义。
不是复制一份很长的规则清单，就等于已完成自动化质量检查。

来源：[code-review 技能](https://github.com/TencentCloudBase/skills/blob/930c3e4f75d3f3ae5ffd49fbd7ec216f344b6b66/skills/cloudbase-code-review/SKILL.md)；
[实际检查器参考代码](https://cnb.cool/tencent/cloud/cloudbase/CloudBase-AI-Toolkit/-/git/raw/main/config/source/skills/cloudbase-code-review/references/lint-rules/README.md)。

## 四、阿里云：把契约、执行和测试连起来

### 4.1 清晰需求下不重复确认

百炼受管 Agent 技能明确强调当轮交付，原文 “deliver in the current turn”；
并禁止同一确认问两遍，原文 “Do not request the same confirmation twice”。
这比只有“尽量少问”更接近用户当前目标：在既定范围内推进，而不是把开发变成连续访谈。
生成模板或建议的任务不应强制登录云服务；实际 apply/destroy 仍要按计划与授权处理，
已获得的确认只覆盖同一未变化计划，不自动扩展到新对象或新影响。

这不代表所有云写入默认获授权。其 live 烟测脚本只有显式 `--execute` 才进入真实执行，
默认路径不读取凭证、不创建资源。本轮只阅读，未运行 live 或 mock 测试。

### 4.2 文档契约与真实模块测试

样本包含 `api-contracts.yaml`、调用模块、烟测和单元测试，形成可检查链条。
API 契约明确是场景范围内的子集，不是 live OpenAPI 的完整镜像；
迁移时也应声明契约来源和覆盖范围，不能把几组示例响应叫完整 API 支持。

`test_cookbook_smoke.py` 直接导入真实模块测试，不是凭记忆另写一份逻辑复刻。
它覆盖了旧轮完成信号不能充当新轮完成、assistant 声称成功不能替代工具输出、分页保留作用域等问题。
这里最值得借鉴的是：测试针对真实失败机制，而且测试的就是交付实现。

### 4.3 真实环境和资源清理也有边界

脚本检查 HTTPS 与指定服务域，先通过只读 GET 验证 key 和 endpoint，再进行 mutation。
live 场景使用本次运行的资源 ledger，在 finally 中清理该次资源；
不能把“烟测要清理”推广成可以删除其他历史资源。

CADT 样本提供 Draft7 输入/输出校验、doctor 和测试，体现预检与契约落地。
但它仍存在强制 G4 STOP 再确认，以及上下文不足时建议跳过产物复核的文字。
前者不宜机械推广，后者不能作为验证豁免：应压缩上下文或明确未验，而不是自动宣称完成。

来源：[百炼受管 Agent](https://github.com/aliyun/alibabacloud-aiops-skills/blob/master/skills/aiml/agent/alibabacloud-bailian-managed-agent/SKILL.md)；
[CADT 部署](https://github.com/aliyun/alibabacloud-aiops-skills/blob/master/skills/migrationom/bpstudio/alibabacloud-cadt-deploy-on-aliyun/SKILL.md)。
读取时 ref 为 master，固定文件 blob 和关联脚本见[公开样本来源记录](公开样本来源记录.md)；blob 不等于 commit。
上述机制来自静态源码和指令，没有据此宣称外部权限、烟测或产品质量已经验证。

## 五、字节：运行时不再反复临时拼脚本

DeerFlow 的 data-analysis 是一个小型执行包：技能入口、开发维护约定和 `scripts/analyze.py`。
脚本承载数据加载、查询、缓存和导出，让模型把精力放在分析目标上，而非每次重写处理程序。
静态实现可见名称防冲突、参数化 SQL、内容哈希缓存，以及 JSON 导出前对重复列名/非有限值的拒绝。
这对应原经验包“封装重复工作”的建议，但多了实际实现与针对产物的校验。

适合迁移的是：只有重复且确定的操作才封装；明确状态变化与资源身份；导出前核对真实约束。
不应把“脚本稳定”理解成完全离线：加载路径仍执行 DuckDB spatial 扩展安装与加载，
即使只处理 CSV 的冷启动也可能有外部依赖；文档 .xls 支持与 openpyxl 分支存在兼容性疑点，尚未实测。

本次看到测试目录存在，但进一步读取测试正文遇公开 API 限流，未把目录存在冒充测试覆盖或通过成绩。
来源：[data-analysis 目录](https://github.com/bytedance/deer-flow/tree/b537d9c16c84e432ee609da57f042d4926c94f8c/skills/public/data-analysis)；
[analyze.py](https://github.com/bytedance/deer-flow/blob/b537d9c16c84e432ee609da57f042d4926c94f8c/skills/public/data-analysis/scripts/analyze.py)。

## 六、评估补强：不要只问“生成的内容看起来对不对”

### 6.1 有用的评估框架

Anthropic skill-creator 明确区分新 skill 对无 skill、修改版对旧版，
相同用例分别运行，保存产物、断言、证据、耗时和 token，并做结果汇总。
它还区分任务输出评估与 description 触发评估。强制加载技能测试成功，不等于自动触发准确。

这正是原经验包最需要落地的部分：用对照证明新增规则是否有用，
观察执行轨迹中是否多读文件、重复询问、绕圈或重写相同脚本，而非只看最终文本。

来源：[skill-creator/SKILL.md](https://github.com/anthropics/skills/blob/ca45fc496a3436251f191354091d557da31c15b5/skills/skill-creator/SKILL.md)。

### 6.2 公开评估器也不是可以盲信的真值机

静态读取发现：
- run_eval 对首个工具有特定观察假设，错误或超时也可能并入“不触发”；负例因此可能被错误算对。
- aggregate 缺评分会跳过、缺指标可能填零，缺 token 时回退输出字符数；这些不等于实际零成本或 token。
- run_loop 按 test 结果挑最佳版本，该批 test 实际参与选型，不是独立最终验证集。

因此本包没有照搬脚本，而是规定：基础设施失败单列，缺指标为 null，空检查不算通过；
基线名称明确绑定；被用来选优的样本不再当最终独立验证；另留未参与调整的样本。
这些是根据源码风险提出的补强，不是声称本轮已运行并修好了上游工具。

来源：[run_eval.py](https://github.com/anthropics/skills/blob/ca45fc496a3436251f191354091d557da31c15b5/skills/skill-creator/scripts/run_eval.py)；
[aggregate_benchmark.py](https://github.com/anthropics/skills/blob/ca45fc496a3436251f191354091d557da31c15b5/skills/skill-creator/scripts/aggregate_benchmark.py)；
[run_loop.py](https://github.com/anthropics/skills/blob/ca45fc496a3436251f191354091d557da31c15b5/skills/skill-creator/scripts/run_loop.py)。

## 七、优化优先级：哪些现在就该补，哪些按需补

| 优先级 | 原包到新闭环的差距 | 落地方式 |
|---|---|---|
| P0 | 少问原则还未成为清晰任务执行契约 | 明确直接推进与只暂停相关动作的条件 |
| P0 | 需求与测试没有追踪关系 | 核心需求对应实现位置与检查方法 |
| P0 | 测试示例尚无真实执行证据 | 隔离输入运行，保存产物、错误和结果 |
| P0 | 触发与执行容易混称 | 自动触发型单独测正负例；无法测就标未运行 |
| P1 | schema 纪律不等于代码防护 | 真实参数校验、退出码和产物范围检查 |
| P1 | 无法证明修改版更有用 | 旧版/无 skill 同条件对照，并保留最终样本 |
| P1 | 环境和发布仍是检查清单 | 预检、依赖版本、许可、宿主与安装验证 |
| P2 | 稳定性与成本尚未量化 | 重复测量、波动、真实成本和适用组合 |

P0 不是每个 skill 都强制全套：只读简单任务无需云适配器或 live 烟测；
只显式调用的工具不必把自动触发当必须通过项；没有脚本就不造脚本凑目录。

原调研新增两份直接可用材料，其内容由主代理整合至[技能开发经验包](技能开发经验包.md)：
- 开发执行协议：接任务、追踪、架构、预检、四层验证、恢复与交付。
- 落地验收表：已有内容、完成证据、优先级，以及 passed/failed/blocked/not_run 状态。

它们是对原包的增量，不替换[PPT 样本分析](PPT样本分析.md)，不安装任何云 skill，也不改变宿主权限。
具体迁移材料导航由[入口](入口.md)承接；本文不依赖旧调研会话的绝对路径运行。

## 八、验证边界与最终结论

原调研仅公开资料和源码静态分析，未安装或执行企业技能，未读取云凭据、创建资源或修改远端系统。
原经验包协议经过独立读者问答检查，不能把文档验收当目标 skill 实际运行或自动触发证明。
公开样本的优点与缺陷同时报告；没有根据企业归属给分，也没有声称它们普遍优于原经验包。
原调研文档校验记录和未运行范围见[公开样本来源记录](公开样本来源记录.md)；归档不新增运行结论。

真正的改善方向是：**从“如何写 skill”升级到“agent 如何完成一次 skill 开发任务”。**
这包括按清晰任务直接推进、把要求落到实现和测试、正确处理未知与失败，以及对交付结论负责。
经验包原调研已补齐协议层；实际可运行程度必须在下一次具体 skill 的实现与测试结果中证明。
