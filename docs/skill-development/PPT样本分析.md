# PPT 样本分析

Skill 架构与开发方法，是把用户意图转成可执行、可验证流程的一组组织方式。
本报告以 WorkBuddy PPT 插件为样本，分析结构、需求理解、精确表达和质量控制，
再给出可迁移方案；它不是 PPT 制作教程，也不是目标插件的安装指南。

适用范围（applies_to）：样本结论仅针对上述版本；迁移原则不等于其他宿主已支持相同能力。
成熟度（status: budding）：已形成可复用方案，尚未用本包模板开发并运行一个新 skill。
核实状态（verified: partial）：源文件事实已静态核对；外部工具、渲染效果和提效幅度未运行验证。

归档说明：本文由原调研材料《总结方案》归档，事实、数字、版本和验证结论均沿用原调研记录。
文中“本次”“本包”涉及样本扫描和验证时，指原调研，不表示归档时重新执行。
样本内部的英文文件名与行号是来源定位，不是本归档目录中的可执行依赖。
归档导航见[入口](入口.md)；可迁移方法与模板由主代理整合至[技能开发经验包](技能开发经验包.md)。

## 一、核心结论：复用决策与契约，不照抄提示词

最值得学习的不是“提示词写得长”，而是把不确定的创作拆成可控过程：
**短入口负责选路，工作流负责顺序，参考文件负责专业细节，工具负责确定性操作。**

这个样本尤其值得借鉴五点：
1. 创建、理解、编辑按真实意图分开；“问一下”不会自动变成“改一下”。
2. 需求先对齐，再收集证据、选择场景、制定设计，最后生成。
3. 用 `DESIGN.md` 固化内容与视觉决策，用逐页 `.slide` 固化生成输入。
4. 用字段表、示例、条件和失败分支代替“专业、合理、高质量”之类口号。
5. 逐页检查、修复同一页、通过后继续；完成后明确结束，避免无意义重复劳动。

但它不是可以原样复制的标准答案。需求字段数量、部分设计规则、场景验收存在不一致；
专有工具依赖与验证承诺也不能脱离宿主照搬。优秀经验应连同边界一起提取。

## 二、目录结构、核心组成与整体设计

### 2.1 先分清插件、skill 和运行产物

原调研给出的是**插件版本根目录**，真正的 skill 位于 `skills/workbuddy-pptx/`。
插件清单负责宿主发现，skill 负责行为指令，运行产物不属于安装目录。

    │   ├── cli/

    │   │   └── slide-tools.md      # 编辑侧工具目录

组件包括 Slide、Box、Text、Image、SVG、Chart、Table、FAIcon、CodeBlock、
Math、QRCode、Hyperlink、Animation、Diagram。

本次扫描共 **30 个文件、282,196 字节，约 275.6 KiB**：27 个 Markdown、2 个 Python、1 个 JSON。
`SKILL.md` 按 `splitlines()` 统计为 18 行；阅读工具可能额外显示末尾空行。
没有发现独立的测试、依赖锁定、模板资产目录，也没有发现 `slidep` 编译器实现。
这说明此包依赖外部运行能力，不证明这些能力在宿主中不存在。

来源：插件清单、`SKILL.md:1–18`。

清单历史与证据边界见[PPT 样本证据与验证](PPT样本证据与验证.md)。

### 2.2 三条流程并非三份相似提示词

| 流程 | 核心过程 | 产物或边界 |
|---|---|---|
| 创建 | 对齐需求、收集材料、设计、创建空白文件、逐页写入检查 | `DESIGN.md`、`.slide`、`.pptx` |
| 理解 | inspect 提取结构、读取相关页、按证据回答 | 不改源文件；信息不足直接说明 |
| 编辑 | 查 schema、定位真实实例、编辑、保存 | 修改指定对象；不擅自关闭用户视图 |

创建不是直接“主题→PPT”。`DESIGN.md` 是决策中间产物，`.slide` 是执行中间产物。
前者表达要讲什么和怎么组织，后者使用受限 JSX 形式的领域特定语言，按文档约定编译成 OOXML。
编辑则切换到已有文档对象操作，避免把局部修改当成重新生成整份文件。

来源：`create-from-scratch.md:26–98,119–155`；`understand.md:3–39`；`edit-existing.md:19–68`。

### 2.3 整体设计思路：逐层暴露必要信息

初始只需知道三条路径；创建时再读选定场景和通用设计原则；写某页时只读所需组件；
编辑时只查询即将调用的工具 schema。不是把全部 27 份文档一次性塞入上下文。

这是减少无关规则干扰的设计机制，不是本次已经测得的 token 或耗时收益。
也不要因入口很短就认定整个 skill 简洁：通用设计文件约 36.9 KB，通用场景约 35.1 KB，
按需加载之后仍应检查重复与冲突。

来源：`SKILL.md:12–18`；`create-from-scratch.md:75–76,100–117`；`edit-existing.md:19–27`。

## 三、一个 skill 的架构应该怎样设计

### 3.1 按变化原因和副作用分层

**入口层**只回答何时使用、选哪条路。不要在这里堆全部工具参数。
**流程层**定义进入条件、输入、操作顺序、每步产物、失败处理和结束条件。
**领域层**存放场景差异；**契约层**定义共同字段、单位、索引、组件参数。
**执行层**封装确定性处理；宿主连接、凭据与平台接口应隔离，避免渗入所有流程。

拆分依据不是“每个文件必须短”，而是：这条规则因什么变化，谁消费它？
例如品牌规范变化不应迫使编辑工具协议改写；工具参数变化也不应改写叙事原则。
简单只读任务可能一个入口文件就够，不要为了形式搭出六层空目录。

### 3.2 公共契约只定义一次，流程引用它

样本把 DESIGN 字段集中到通用原则，组件参数集中到各组件文档，方向正确。
但“公共文档存在”不等于契约已经一致，仍需检查流程引用与例外规则是否匹配。

建议明确每个字段的名称、类型、来源、必填条件、允许未知的方式和消费者。
派生字段不要独立维护两份；场景只补差异，不重复复制公共规则。
样本中 `role` 与 `rhythm` 已有映射，未来可以保存一个、推导另一个，减少漂移。

来源：`references/design-principle.md:313–317,381–446`。字段单一来源与派生建议为本报告补强。

### 3.3 模块必须可发现，也必须有明确加载时机

每份参考文件都应能回答：“哪个入口在什么条件下要求读取我？”
文件存在不代表流程会用到它。样本有 6 个场景文件，主流程只列 5 个场景；
`consulting.md` 未出现在主路由中，本次也未找到从其他样本文件进入它的明确路径。
不推断作者是有意保留还是遗漏，只把它作为可达性检查案例。

建议发布时验证本地链接、场景注册表与文件清单是否一致；无入口的资料注明其地位或移除。
来源：`create-from-scratch.md:59–71`；场景文件清单。

### 3.4 将可恢复状态放进产物，不只留在对话里

每页单独源文件便于局部检查与修复；编辑流程要求使用真实 `file_id`，不把文件路径当实例 ID。
编辑之后重新读取，避免继续使用旧页码或旧形状索引。这里的价值是维护对象身份，而非记住某个命令。

未来复杂任务可保存最小状态：任务契约、稳定对象 ID、修改范围和已通过的检查。
这是扩展建议；样本逐页索引仍由 Agent 维护，并不等于已经实现持久化事务或恢复日志。
来源：`create-from-scratch.md:119–144`；`edit-existing.md:39–68`。

## 四、如何理解真实需求，而不是靠猜测

### 4.1 先区分“要做什么”和“希望怎么呈现”

先识别创建、读取、编辑或只要建议，再识别目标、受众和范围，最后处理风格。
“把这一页讲清楚”可能是问答，也可能是改稿；没有写入意图时，先保持只读。
用户说“做得有说服力”，不代表允许编数据，也不代表一定要制作支持某一结论的材料。

样本要求只问缺失信息、集中提问，非硬阻塞项默认推进；页数优先服从用户或逐页大纲。
重点不在固定问几个问题，而在**只问会改变接下来动作的问题**。
来源：`SKILL.md:14–18`；`create-from-scratch.md:26–55`；`understand.md:3`。

### 4.2 用证据状态消除“默认等于需求”的错觉

建议把关键值分为四类：用户或材料明确提供、基于证据推断、可逆默认、未知。
每项同时保存来源和猜错代价。前三类不能混写成“用户要求”。

目标文件和修改范围不明，可能写错对象，应阻止相关写入；字号偏好不明通常可以先采用可逆默认。
用户给了品牌色但没有字体，只补缺失字体，不把局部默认变成整体重新设计。

四态记录是本报告补强；样本已有“有材料优先沿用、缺项兜底”的机制，但未统一建立这份台账。
来源：`references/scenarios/academic.md:15–39`；`create-from-scratch.md:30–37`。

### 4.3 路由依据是用途和受众，不是一个关键词

学术场景针对汇报研究成果，明确排除教学课件；因此“给高中生讲量子物理”不能仅因科学主题走答辩风。
投资分析对应投委会、估值、尽调等判断任务；没有明确垂直命中时使用通用路线。

每个场景建议写：适用条件、排除条件、所需证据、特有输出、缺信息处理。
这样选择场景可以被复核，而不是“感觉这个风格更高级”。
来源：`create-from-scratch.md:63–71`；`references/scenarios/academic.md:3–7`；
`references/scenarios/investment-analysis.md:3–12`。

### 4.4 不足以确认时，允许得出“不知道”

理解流程规定：关系和方向要有明确连线、箭头或分组，不能根据颜色或位置作确定结论。
投资分析区分披露事实、测算、预测和研究判断；学术场景禁止编造文献、数据和公式。

可复用原则是：**输出结论的强度不得超过输入证据的强度。**
缺信息时可以检索、缩小结论、标注未知或报告阻塞，不得为使版面完整而制造事实。
来源：`understand.md:18–28,34–39`；`references/scenarios/investment-analysis.md:25–31,247–251`；
`references/scenarios/academic.md:90–99`。

## 五、如何简洁精确，避免正确但空洞的话

### 5.1 一条规则必须改变行为

“保证质量”“充分理解需求”即使正确，也没告诉执行者如何选择。
更好的规则包含具体触发条件、动作、对象、判断标准；必要时补失败处理。
样本的“用到一个工具查一个 schema”“必填项、0-based、pt 核对后再调用”就可以直接执行。

| 空话 | 可执行写法 |
|---|---|
| 准确理解需求 | 写入前确认目标文件与修改范围；未知时不写入 |
| 正确使用工具 | 读取本次工具的 schema，核对必填项、类型、索引和单位 |
| 提供可信内容 | 数字附来源、日期和单位；缺来源时不把估计写成披露事实 |
| 输出简洁专业 | 删除不改变结论的流程旁白，保留证据和必要限定条件 |

来源：`edit-existing.md:19–33`；其余改写是可迁移示例，不是原文引用。

### 5.2 删除元叙述，保留真正的信息

通用原则要求删掉目录数量统计、阅读顺序复述、主线预告等无新增信息的文字；
投研场景明确禁止“本章将讨论”“本章要回答的问题”之类占位式句子。

一个有效的删句测试：删掉后，事实、动作、约束和验收是否完全不变？若是，优先删除。
另做“替换对象测试”：把行业或对象换掉仍处处适用的句子，往往缺少当前任务的独有信息。
样本将“随着XX的发展，YY面临新的机遇与挑战”归为拿掉专有名词后到处能用的万能句式。
但不要删掉数字口径、适用条件、来源与不确定性；这些不是废话，而是防止误读的必要信息。
来源：`references/design-principle.md:230–234,290–297`；
`references/scenarios/investment-analysis.md:142`。

### 5.3 用例子规定分辨率，不用形容词堆气势

样本把“用户规模分析”改成“用户规模增长已放缓”，把“擅长沟通”改成可核实的活动经历。
这些例子的价值是教会模型：主题标签不是结论，自我评价不是证据。

但结论句不能反过来诱导编造。没有趋势数据时，不应硬写“增长放缓”；
原文“12 场、500+ 人”只是示例数字，迁移时必须换成用户实际证据，或明确未知。
来源：`references/design-principle.md:252–272`；`references/scenarios/personal-introduction.md:18–29`。

### 5.4 简洁来自合理组织，不来自压缩成暗语

入口短、参考按需读，是结构简洁；参数表、最小例子和限制说明，是表达精确。
它们应一起使用。不要把关键信息压成只能靠作者补充解释的词组，也不要把所有规则改成“禁止”。
禁令最好对应一个已知失败，再给替代动作；否则模型知道不能做什么，却仍不知道应该做什么。

组件文档有两个可直接借鉴的写法：Chart 明确 `barDirection` 取 `bar` 或 `column`，
并排除容易猜出来的 `horizontal`、`vertical`；Hyperlink 不支持段内链接时，
给出拆成多个 Text 后用 Flex 拼接的替代方式。前者消除猜参数，后者消除失败后的无路可走。
来源：`references/dsl/chart.md:120–139`；`references/dsl/hyperlink.md:49–52`。

## 六、其他值得借鉴的工程实践

**先查契约，再执行。** schema、单位、索引和参数名应来自当前工具，不来自记忆。
这比增加一句“调用时小心”更可靠。来源：`edit-existing.md:19–33`。

**只读能力单独设计。** 理解不是简化版编辑；只读流程明确禁止写工具，并按问题定位材料。
这同时减少越权和无关信息。来源：`understand.md:20–32`。

**区分文件、内存实例和用户视图。** 打开后台对象不等于用户能看见；呈现路径也不等于实例 ID。
编辑后还需要保存。其他 skill 中也应区分磁盘文件、会话对象、远端资源和最终交付物。
来源：`edit-existing.md:35–66`。

**缩小修复单元。** 逐页写入后检查，失败替换同一页，不重新追加一份错误副本。
这一机制适合分段文档、批量记录等任务；但不能据此声称已解决写入超时与事务恢复。
来源：`create-from-scratch.md:119–144`。

**用关系选表现形式。** 层级、流程、转化和并列信息不是同一种结构，不应全塞卡片。
迁移时先识别数据关系，再选组件或工具，不把某种造型当所有任务的默认答案。
来源：`references/scenarios/general.md:170–184`。

**完成有终点。** 成功后停止无关操作，用户沟通描述成果而非工具流水账。
迁移时应保留必要的失败披露和审计信息，不能把“不暴露实现”理解为隐瞒问题。
来源：`create-from-scratch.md:146–155`；`understand.md:34–39`。

## 七、样本的不足与迁移边界

| 问题 | 静态证据 | 应如何处理 |
|---|---|---|
| 需求契约数量漂移 | 创建流程列 4 项，却要求“6 个维度”；通用原则未补定义 | 共享字段契约统一维护，不靠模型补齐 |
| 场景发现不完整 | 6 个文件，主路由 5 项 | 校验注册表、链接与模块清单 |
| 可选与必填矛盾 | 允许纯结构页仅 L3，字段表却要求 L1 图片占位 | 必填规则带适用条件，不为过关造素材 |
| 验收参数冲突 | 咨询标题基准为 y=60，检查项又要求 y=44 | 数值单一来源，执行前消除冲突 |
| 平台和验证不可直接迁移 | 依赖 slidep、编辑器服务、present_files；实现不完整包含在包中 | 先验证宿主能力，再决定流程 |

对应来源：`create-from-scratch.md:28–37,59–71,154`；
`references/design-principle.md:3–5,339–345,435–446`；

## 八、可以直接借鉴的总结方案

未来开发 skill，采用以下顺序，而不是先写长篇提示词：
1. 定义真实任务、非目标、输入输出和副作用边界。
2. 准备几个真实请求，区分正常、缺信息、只读与失败恢复。
3. 用最小入口实现路由，只在流程或领域差异出现时拆模块。
4. 定义共享契约，记录事实、推断、默认与未知，不让模型猜字段。
5. 把复杂决策写进中间产物，把确定性重复操作做成脚本。
6. 每条规则写出可观察动作或判据，用少量正反例约束模糊词。
7. 测试最终产物和执行过程；将真实失败转成回归用例，而不是不停加禁令。

这是一套建议方法，不是声称样本已经具备完整测试体系。
原调研的开发模板与检查清单所涵盖的入口、流程、需求记录、规则改写和发布清单，
由主代理整合至[技能开发经验包](技能开发经验包.md)，具体材料导航见[入口](入口.md)。
完整来源、静态覆盖与原调研文档验收见[PPT 样本证据与验证](PPT样本证据与验证.md)。

最终判断标准不是“skill 看起来是否专业”，而是：
**在一个未见过的真实请求里，它能否基于证据选对动作，并让结果、失败与未知都可核对。**
