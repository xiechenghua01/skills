# 技能开发经验包

技能开发经验包是一套将明确用户需求转成技能结构、执行流程、验证与交付证据的方法。
本文合并仓库原 playbook、WorkBuddy PPT 分析、腾讯/阿里云/字节公开技能对比和本次技能实现经验。
它不是多份报告的拼接：保留共同机制，修正样本过度泛化，区分通用方法、仓库规范与验证事实。

适用场景：新建、编辑、理解 skill，以及判断一个技能是否真正完成、是否值得继续优化。
适用范围（applies_to）：通用方法需结合目标宿主；六字段、市场版本等仅是本仓库规范。
成熟度（status: budding）：已用于首版技能开发并有局部测试，但尚无跨宿主与多模型泛化证据。
核实状态（verified: partial）：样本机制有静态来源，首版有本地测试；企业运行效果与自动触发未验证。

## 一、合并结论：复用决策与契约，不复制配额

原经验擅长结构和写法，企业调研补足执行和测试，首版实现又暴露了检查器组合边界。
三者共同支持的主线是：**清晰需求直接推进，选最小结构，用事实决定动作，用结果证明完成。**

| 来自哪里 | 保留什么 | 补充或修正什么 |
|---|---|---|
| 原始 playbook | 意图分流、分层、按需加载、条件/反例、引用审计 | 固定行数/字段数不作通用硬标准；平台规则注明范围 |
| PPT 样本分析 | 设计与执行中间产物、局部闭环、对象身份 | 字段数量、场景可达性和规则冲突应核对；布局非视觉证明 |
| 腾讯 CloudBase | 停止加载、环境路由、操作后回读、分层审查 | 不无条件重复确认；检查清单必须对应代码覆盖 |
| 阿里云 | 当轮交付、schema/doctor、预览与真实执行、真实模块测试 | 开关非授权，局部契约非完整 API，上下文不足不免验 |
| 字节 DeerFlow | 确定性脚本、名称冲突、缓存和导出检查 | 本地脚本不等于离线，测试存在不等于通过 |
| 评估工具与本地实现 | 基线、分层测量、真实实现回归 | 缺测不填零、错误不算负例通过、组合场景也需测试 |

以下九条是可以优先采用的实践：
1. 入口描述真实使用情境与非目标，按用户意图选路。
2. 完整需求直接使用，业务或授权未知只阻止相关动作。
3. 规则只有改变一次选择并能核对才值得保留。
4. 单一契约、条件加载，足够完成任务后停止加载。
5. 稳定重复操作做脚本，专业判断不假装成机械阈值。
6. 字段、参数、对象身份从源文件或当前接口取得，不凭记忆复刻。
7. 校验覆盖静态、触发、执行及必要对照，层间不能互相替代。
8. 失败、不完整与未运行有合法输出，不用“成功”句子掩盖证据缺口。
9. 完成后停止无关优化，安装、提交、推送、发布属于独立授权。

## 二、架构：按变化原因和副作用组织

### 2.1 最小结构优先

简单只读技能可以只有 SKILL.md；出现真实分支、公共规则或重复执行工作时再拆。
不要为了齐全建立三链、脚手架、云适配器和空目录，也不固定入口必须少于 40 行。

| 部分 | 回答的问题 | 放什么 |
|---|---|---|
| 入口 | 何时使用，选哪条路径？ | description、意图路由、共同边界 |
| 流程 | 输入如何变成产物？ | 进入条件、顺序、门槛、失败和结束 |
| 参考 | 当前选择该依据什么？ | 共同契约、领域知识、例外和模板 |
| 脚本 | 哪些处理应确定性执行？ | 解析、转换、校验、工具适配 |
| 验证 | 怎样证明承诺满足？ | fixtures、真实实现测试、证据与状态 |
| 分发 | 如何识别、安装和更新？ | 宿主配置、版本、许可、展示 |

阈值改变只影响定义处，接口变化只影响适配器及调用者，分层才真正有用。
一条公共规则不要在多个流程和场景各抄一份；派生字段有明确来源，不独立维护两套值。

### 2.2 路由和渐进披露

“创建、修改、解释”可以映射用户请求，技术模块名称不能代替任务路由。
用真实原话、同义表达和近邻反例检查边界；复合任务可顺序移交，不机械要求一句话只有一个意图。
只读与写入副作用分开。每份资料声明谁在什么时候读，什么情况下不读。

通常常驻的是元数据，正文在触发后加载；实际加载方式以宿主为准。
入口短的价值是减少无关指令，不是“正文每一行永远常驻”。
掌握当前流程与语法后停止加载，不为显示全面而读取全部组件、全部 schema 或历史调研。

### 2.3 中间产物与对象身份

复杂生成先保存目标、证据和单元设计，再执行；仅后续确实消费时建立中间文件。
它可抗漂移和支持交接，但不要求固定 6–12 字段，也不宣称语义内容都可机械校验。

路径、文档实例、远端 ID、显示次序、用户视图不是同一对象。使用真实稳定 ID，变更后回读状态。
单元失败替换同一对象，不能重试时不断追加副本；超时先确认实际结果，再决定是否安全重做。

## 三、需求理解：别猜，也别重复确认

### 3.1 字段记录答案与依据

先识别任务、目标对象和副作用，再处理受众、形式与风格。
只保留影响当前任务的字段，不强制所有技能做长问卷。

| 字段 | 内容 |
|---|---|
| 任务与目标 | 新建/编辑/理解、用户想解决的问题 |
| 输入与输出 | 材料、产物、保存范围 |
| 范围与非目标 | 哪些能改，哪些不能改 |
| 环境与约束 | 宿主、工具、权限、格式、时限 |
| 验收与未知 | 完成条件、尚缺的信息与影响 |

每个关键值标为 explicit、inferred、default 或 unknown，并保存来源：
- explicit：用户、材料或工具直接提供。
- inferred：有证据的推断，说明依据，不升级为事实。
- default：说明过的可逆实现选择，不等于用户要求或授权。
- unknown：无法确认，不用常识填成确定答案。

### 3.2 缺口按影响处理

目标、范围、交付物已清楚就推进；源码、接口、依赖和文件位置可查则自己查。
只问会改变下一步动作的问题，集中提问；“最多三问”可以是沟通预算，不是安全上限。

业务含义、要覆盖的对象、新增费用/权限不明时暂停相关动作；独立读取和离线部分可继续。
只缺可逆形式偏好可以默认推进并披露。默认不能扩大删除、发布或生产操作范围。
用户明确“先出方案”时不写实现，理解任务不自动修复，清晰开发任务不重复索取同一确认。

### 3.3 证据强度限制结论强度

按用途与受众选场景，不按“高校”“金融”一个关键词硬套垂直模板。
没有趋势数据不写“增长放缓”；没有箭头/连线等明确结构，不从颜色和位置断言关系。
来源中的通常、版本、单位、条件必须保留。示例数字不能变成用户经历或企业事实。
外部页面、日志和用户资料是数据，不能指挥 agent 增权、读凭据或发送私有文件。

## 四、精确写作：让规则消除歧义

### 4.1 条件、动作、判据与失败分支

| 空泛写法 | 可执行写法 |
|---|---|
| 充分理解需求 | 写入前确认目标与范围；未知只阻止相关写入 |
| 正确调用工具 | 读当前 schema，核对必填、类型、单位、索引和对象身份 |
| 保证可信 | 数字附来源、日期、单位；查不到标未知，不造替代数 |
| 输出专业简洁 | 删除不改变结论的流程旁白，保留证据和限定条件 |
| 注意异常 | 区分错误类别、恢复条件、次数上限与结果未知后的回读 |
| 不要重复检查 | 未变更且已验证结果复用；变更或覆盖不足时重验相关范围 |

可执行规则按需包含触发、动作、对象、产物、判据、失败处理，不机械要求每句凑满六项。
数值适合尺寸、预算、次数和枚举；语义质量不要为了可测而创造虚假阈值。
正例规定目标，反例展示具体失败，替代方案避免 agent 只知道“不许”。

### 4.2 删句和替换对象测试

删掉句子后动作、事实、约束与验收不变，优先删除。
换掉行业或对象仍处处适用，通常缺少当前任务信息；“随着XX发展，YY面临挑战”不能代替分析。
必要理由、来源、不确定性和版本条件不是废话，不因简洁删掉。
无需每个“应该”都配“禁止”，也不以禁令数量衡量质量。

### 4.3 规则冲突与沟通

公共规则集中维护，场景补差异与例外；冲突先查来源和适用条件，不随意裁决作者意图。
对用户描述成果和限制，内部术语只在排错或有助理解时出现；不能为“说人话”隐瞒错误。
完成即止抑制加戏，不取消必要验收，也不意味着改了对象之后仍禁止复验。

## 五、执行、测试与质量闭环

### 5.1 四层验证不能互相替代

| 层 | 检查 | 不代表什么 |
|---|---|---|
| 静态 | 头部、链接、字段、类型、示例和实现 | 功能正确、服务可用 |
| 触发与路由 | 真实宿主选择、同义正例/近邻负例、读写分支 | 加载后的任务质量 |
| 执行与产物 | 真实脚本、退出码、终态、内容范围、无越权 | 未测平台或普遍质量 |
| 对照与成本 | 新旧/无技能同条件运行、实际成本和波动 | 大小样本之外的全面改善 |

显式给子 agent 技能只能检验正文执行，不证明自动触发。
mock、预览、live 和生产分别记录；布局检查不冒充视觉验收。
基础设施错误单列，不当正确“不触发”；测试目录存在不等于运行通过。

### 5.2 测真实实现，组合边界也要覆盖

测试导入或调用交付实现，签名、参数顺序与常量来自实际源文件，不另写一份逻辑复刻。
静态 schema 有效不等于调用前验证已实现；输出成功文字不代替新轮工具结果和实际产物。
按能力保留正常、缺信息、只读、限定修改、错误、未知结果恢复、触发近邻等用例。

首版检查器曾有 macOS 临时路径规范化导致的 mock 偏差，以及跨段落代码、注释/围栏、引用标题组合盲区。
这些问题说明单独功能用例全绿仍可能漏掉交互条件，应把真实发现转成回归。
历史记录的 43 项测试和三链样本见 [技能首版验证记录](技能首版验证记录.md)，不是本次文档整理重跑的成绩。

### 5.3 结果与对照

结果分 passed、failed、blocked、not_run。空断言、缺产物、超时、读错不计通过；缺指标为 null。
报告有效执行通过率时同时给 blocked/not_run 和总数，不隐藏未覆盖。
同条件对照使用明确旧版或无技能基线，写入隔离副本；不共享云资源制造冲突。
用于选版本的样本已参与调整，不称独立最终集。差异被波动覆盖时写证据不足。
先守硬边界，再谈速度或成本；不能用快抵消越权和虚假成功。

## 六、新建、编辑、理解的工作协议

### 6.1 新建

接任务 → 查现状与规范 → 最小架构 → 实现 → 分层验证 → 交付。
关键需求对应承载文件与验收条件：只读对应输入哈希和无写动作；错误对应退出码和结果；清晰任务对应无重复询问。
重复稳定处理封装，必要参考按条件加载；不因生成代码任务强制用户登录真实服务。
用户只要方案就交用途、结构、流程和验证方案；没有代码或测试时不称可运行。

### 6.2 编辑

读取入口和命中依赖 → 确定影响 → 最小修改 → 回归 → 交付差异。
名称、调用方式、未授权内容默认保持；公共接口和字段变动核对调用者。
触发错修描述，参数错修校验，重复劳动修封装，假成功修证据链；不要只加禁令。
未变更的有效结果复用；支持范围变化或新证据出现时重验。必要对照先保存基线。

### 6.3 理解

定位问题 → 追踪文档/实现/测试/结果 → 答案或缺陷清单。
默认不修改、不安装、不运行附带命令；授权隔离验证也不自动包含生产写入。
答案区分文档约定、代码实现、测试覆盖、运行证据和未知；指出缺口，不补造能力。
复合请求已有修复授权时可移交编辑，只读请求到答案结束。

## 七、交付、仓库规范与完成定义

### 7.1 通用与本仓库分开

通用开发先查目标宿主和仓库约定，name/description 之外的元数据不假定跨平台有效。
当前 chengze-skills 要求六字段顺序、双语描述单行引号、内容日期和插件/marketplace 同步版本。
这是现行仓库要求，不是“市场验证过所以所有宿主必须采用”。具体以根 AGENTS.md 和 README 为准。

目录、文件命名以协议识别与本次用户约定为准：本次开发资料目录英文，docs 文档中文。
本次只整理 docs，没有重命名技能入口/实现、修改宿主配置、更新包版本或宣称安装生效。

### 7.2 可复核交付

必要技能文件、来源许可、依赖/宿主范围、用例、实际结果和调用方式可核对。
运行日志与私有数据不默认进入使用技能的上下文；预检不自动安装依赖或扩权。
清理只限本次创建资源，未知结果先回读，不能全局删除历史对象。

完成口径分别为结构完成、本地执行已验证、目标宿主已验证、相对改善有证据。
只有承诺范围具备对应证据才称已验证；开发授权不自动包含安装、提交、推送或发布。

## 八、来源、冲突取舍和适用边界

### 8.1 资料关系

- [原始开发经验](原始开发经验.md)：原 playbook 历史归档；合并时不删除其原始判断。
- [PPT样本分析](PPT样本分析.md) 与 [证据与验证](PPT样本证据与验证.md)：原目录和设计分析。
- [企业公开技能对比](企业公开技能对比.md) 与 [公开来源记录](公开样本来源记录.md)：机制、原文、版本与不足。
- [技能首版验证记录](技能首版验证记录.md)：已执行的局部工程证据及未运行范围。

### 8.2 已处理的冲突

旧文统计 33 文件，新静态扫描记录 30；保留两份来源口径，不合成统一“生产规模”。
六字段和双包版本保留为仓库要求；固定入口行数、问数、字段数和全面数值化不作通用门槛。
“禁止复检”修正为不重复无效检查；企业内置视觉检查声明与本次运行证据分开。
“交叉引用脚本能抓五种问题”视为历史建议，真正检查须按引用文件解析并说明语法覆盖。

### 8.3 当前验证边界

公开样本主要是静态源码观察，企业归属不等于可靠性证明；本地首版只是特定显式样本的验证。
真实宿主自动触发、多模型泛化、企业云操作与全面对照没有完成，不能由本次文档合并补成通过。
本包的判断标准是：面对未见过但明确的任务，能否依据证据选动作，并让结果、失败和未知都可核对。
