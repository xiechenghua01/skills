## 1. 解剖：这份 skill 的骨架

### 1.1 目录结构与职责

```
skills/workbuddy-pptx/
├── SKILL.md                    18 行   路由层：frontmatter 触发词 + 3 行分流表
├── create-from-scratch.md     155 行   流程层：生成链（Step 1–6）
├── understand.md               39 行   流程层：理解链（只读，不改源文件）
├── edit-existing.md            80 行   流程层：编辑链（实时可视化编辑）
├── references/
│   ├── design-principle.md    488 行   知识层-通用：审美硬指标 + DESIGN.md schema
│   ├── scenarios/         195–286 行   知识层-垂直：6 套风格（通用兜底 + 5 个垂直）
│   ├── dsl/                27–266 行   知识层-组件：14 份组件手册（按需读）
│   └── cli/               116–138 行   知识层-工具：命令行与 90+ 工具的一句话清单
└── scripts/
    ├── edsdk.py               366 行   执行层：工具调用封装（list/schema/call）
    └── doc_image_extractor.py 490 行   执行层：从文档抽取图片
```

体积分布：路由 1 个（18 行）、流程 3 个（274 行）、知识 22 个（约 3348 行）、执行 2 个（856 行）。

**关键比例**：入口 0.4%，流程 6%，知识 75%，执行 19%。入口极薄是刻意的——它每次会话都会被加载，厚 1 行就是 1 行的常驻成本；知识按需加载，可以厚。

### 1.2 三条链路的文件流

| 链路 | 读取顺序 | 产出 |
|---|---|---|
| 生成 | SKILL → create-from-scratch → scenario → design-principle → dsl/*（按页按需） | `DESIGN.md` + `slides/NN.slide` + `.pptx` |
| 理解 | SKILL → understand → slidep inspect → `slides.md` | 只读答案，源文件不动 |
| 编辑 | SKILL → edit-existing → slide-tools → edsdk schema → call | 修改后的 pptx（保存不关闭） |

三条链**不共享正文**，只在 `SKILL.md` 交汇。`edit-existing.md` 首行声明"上级：[SKILL.md]"，`understand.md` 首段声明"要改就转 edit-existing"——靠两句话完成链路间的移交，而不是复制规则。

### 1.3 整体设计决策（我的判断）

1. **把"能力"拆成"意图"**：用户不会说"我要走 DSL 编译链"，只会说"做一份 PPT / 看看这份 / 改一下"。分流依据必须是用户原话能命中的词。
2. **把"质量"变成可测量**：审美是最难写规范的部分，它选择用 px、%、倍数、数量上限去锁——因为"要好看"对模型无信息量，"padding ≥ 60px"有。
3. **把"风格"做成数据而不是散文**：6 个 scenario 文件等价于 6 套参数集（配色表 + 字号阶梯 + 布局候选池 + 硬闸门），选型靠一张"调性 / 适用场景"表，而不是让模型自由发挥。
4. **把"校验"交给工具，不交给模型的眼睛**：`slidep lint` 返回结构化 `diagnostics`，并**明令禁止**截图复检。模型自评视觉是最不可靠的环节，能外包就外包。
5. **把"专业术语"关在内部**：`lint`/`upsert-dsl`/`JSX`/`OOXML` 一律不许出现在用户对话里。用户视角只有"页 / 封面 / 目录 / 这一页"。

## 2. 架构：一个 skill 应该怎么分层

### 2.1 四层职责模型

| 层 | 回答什么问题 | 放什么 | 绝不能放 | 体积参考 |
|---|---|---|---|---|
| **路由层**（SKILL.md） | 这次该走哪条路？ | 触发词、分流表、分支入口链接 | 任何执行细节、任何原则 | 15–40 行 |
| **流程层**（每链一个 md） | 分几步？每步的输入输出和门禁是什么？ | 步骤编号、前置条件、校验点、失败分支 | 领域知识正文（只链接） | 60–200 行/链 |
| **知识层**（references/） | 具体怎么做才对？ | 判据、阈值、模板、字段表、反例 | 流程编排（不许反向指挥流程） | 单文件 ≤ 500 行 |
| **执行层**（scripts/） | 怎么调工具？ | 单一入口脚本、参数校验、错误归一 | 业务判断 | 按需 |

判据：**看一段内容改动时会不会牵连其他层**。阈值调了只改知识层 → 分层正确；改一个阈值要同步改三个流程文件 → 知识被复制了。

### 2.2 路由层只做一件事：分流

`SKILL.md` 全文（去掉 frontmatter 只有 8 行）：

```markdown
## 任务路由
| 任务类型 | 执行路径 |
| 创建、生成PPT（含基于上传材料） | 阅读 [create-from-scratch](create-from-scratch.md) |
| 理解已有 PPT / 问答 | 阅读 [understand](understand.md) |
| 编辑已有 PPTX（含生成后的改稿） | 阅读 [edit-existing](edit-existing.md) |
```

三个要点：
- **分流表用用户语言写**（"看这份 PPT""改某一页"），不用实现语言（"inspect""upsert"）。
- **每条路径动词化**（"阅读 X"），不是名词堆（"X 模块"）——模型更容易执行动词。
- **frontmatter 承担触发**：`description` 里塞满真实触发词（做PPT、生成PPT、改PPT、看这份PPT、这一页讲什么、pptx、幻灯片），中英双语各一份。触发靠这里，分流靠表格，两者分离。

### 2.3 切分维度：按意图，不按模块

反例（常见错误切法）：`dsl-parser.md` / `layout-engine.md` / `export.md`——这是代码结构，用户无法命中。
正例：`create` / `understand` / `edit`——用户一句话就能归类。

判断方法：**把用户最可能的 10 句原话列出来，每句都应该能落进且只落进一个分支**。落不进 → 缺分支；落进两个 → 分支边界没切干净。

### 2.4 知识层的三种文件类型

| 类型 | 特征 | 本例 | 何时新建 |
|---|---|---|---|
| **原则型** | 跨场景通用、可量化、常被引用 | `design-principle.md` | 同一条规则在第 2 个场景重复出现时 |
| **场景型** | 一套完整参数集，互相排斥 | `scenarios/*.md` | 有明确的垂直领域（行业 / 体裁 / 受众）且风格显著不同 |
| **组件型** | 单一对象的接口手册，互不依赖 | `dsl/*.md` | 一个可独立使用的能力单元，有独立参数表 |

**场景型必须配一个兜底**。`general.md` 首行就写明"需求未命中任何具体场景时的兜底方案"，路由表还给了判断标准："用户场景是否**明确属于**某风格的特定领域"——防止模型为了用上垂直文件而硬套。

### 2.5 渐进披露的量化规则

它没有把"按需加载"停留在口号，而是给了具体的读与不读：

- 生成链 Step 5 明确：**动笔前按需阅读本页用到的组件文档**，附 14 行组件→用途对照表，不是让人通读 14 份。
- 编辑链明确：**用到一个查一个，不要一次性拉全量 schema**，并给了自检勾选（☐ 已跑 schema / ☐ 已确认必填 / ☐ 已确认 0-based）。
- 理解链明确：只有用户问到备注/批注/母版等，才去用 `slide_get_*`；"普通内容、布局和图片问题不调用 EDSDK"。

可迁移的三条：
1. 每份知识文件头部写清**谁在什么时候读它**（`design-principle.md` 第 3 行就写了调用方）。
2. 给"读什么"的**清单 + 触发条件**，不给"全读"。
3. 明确写"**不需要**读/调用的场景"，比写"需要"更省 token。

### 2.6 命名与目录约定

- 项目产物目录名 = pptx 文件名去后缀；页面文件 `{两位序号}.slide`；资源文件**禁中文、空格、特殊字符**。
- 组件文档名 = 组件名小写（`text.md` / `chart.md`），与代码里的标签一一对应。
- 场景文档名 = 风格名（`academic` / `redgold` / `investment-analysis`），不用编号。

理由都指向同一件事：**名字是给模型做字符串匹配用的**，可预测、可对应，就等于少一次猜测。

### 2.7 入口头部与骨架（可直接抄）

`workbuddy-pptx` 的头部六字段已被市场验证，照它写：

| 字段 | 作用 | 写法要点 |
|---|---|---|
| `name` | 机器标识 | kebab-case，与目录同名 |
| `display_name_zh` | 中文界面名 | 2–6 字短名词（「PPT」「写知识文档」），不加「技能」后缀 |
| `display_name_en` | 英文界面名 | 同样是短名词，不是 `name` 的音译（「Presentation」，不是「Workbuddy Pptx」） |
| `description` | 中文触发描述 | 做什么 + 适用场景 + 触发词，全塞一行 |
| `description_en` | 英文触发描述 | **重写而非直译**：英文用户的问法不同，触发词要各自覆盖 |
| `version` | 内容版本 | `v` + 内容定稿日期：`v20261013` |

**两个版本号分工**（少一个都会出问题）：

| 位置 | 形式 | 谁读 | 何时改 |
|---|---|---|---|
| `SKILL.md` 的 `version` | `v20261028` | 人：这一版内容是哪天的 | 内容改动即改为当天 |
| `plugin.json` + `marketplace.json` | `0.1.3` | 机器：判断有没有更新 | 每次内容改动 z 位 +1，两处同步 |

只留日期版，跨年或手填错日期就失去可比性；只留 `x.y.z`，人看不出内容时效。两个一起写，代价只是每次改两处。注意 `marketplace.json` 才是更新检测的实际依据——插件目录里的版本号改了而市场条目没改，用户端永远看不到更新按钮。

三条写法纪律：

1. **`description` 里必须有用户原话**。「做PPT」「改一下这篇条目」这种用户真会打的字，比「支持演示文稿创作」有用一个量级。
2. **中英双语不是翻译关系**。中文用户说「整理笔记」，英文用户说 "take notes"、"digest a concept"——触发词要各自覆盖，逐字对译会漏掉一半入口。
3. **一行写完、双引号包裹，内部不用 ASCII 双引号**。实测三种写法：

   | 写法 | YAML 解析结果 |
   |---|---|
   | 不包引号 + 内层 `"document"` | 通过（引号在普通标量里只是字符） |
   | 外层双引号 + 内层 `"document"` | **语法错误**：提前结束字符串，`did not find expected key` |
   | 外层双引号 + 内层 `“document”` | 通过 |

   不包引号看似也能用，但有两个坑：值里出现半角冒号加空格（`: `）直接解析失败；出现空格加井号（` #`）会被**静默截断**成注释——后面半段描述消失，没有任何报错。所以统一「双引号包裹 + 内部改用 `“ ”`」，两个坑一起堵。不要用块标量 `|`：朴素解析器会把 `|` 当成字面值。

模板（六字段 + 三行路由，到此为止）：

```markdown
---
name: <kebab-case，与目录同名>
display_name_zh: <中文短名>
display_name_en: <英文短名>
description: "<做什么>。适用于 <3–5 个场景>。当用户 <原话 A>、<原话 B> 时使用——即使没提「<关键词>」，只要意图是 <本质> 就应触发。"
description_en: "<same coverage, rewritten in English with the phrases English users actually type>"
version: v<YYYYMMDD>
---

# <能力名>

## 任务路由
| 任务类型 | 执行路径 |
|---|---|
| <用户话术 A> | 阅读 [<branch-a>](<branch-a>.md) |
| <用户话术 B> | 阅读 [<branch-b>](<branch-b>.md) |

<!-- 到此为止。不写原则、不写步骤、不写工具用法。 -->
```

## 3. 需求理解：把"别猜"变成流程约束

这是这份 skill 最值得学的部分——它没有写"要准确理解用户需求"这种废话，而是给了一套**带门禁和配额的对话协议**。

### 3.1 五个机制

| 机制 | 原文 | 解决什么问题 |
|---|---|---|
| **门禁** | "意图未对齐 → 禁止进入后续任何步骤，不许一边做一边猜" | 模型边做边猜的默认倾向 |
| **配额** | "只问缺失的；一轮问完，文字提问 ≤ 3 个" | 反问变成连环追问，或一个问题都不问 |
| **分级默认** | "非硬阻塞的空缺按合理默认推进"；"只给主题时自行推测合理页数并说明理由" | 把所有空缺都当阻塞，卡死流程 |
| **产物约束** | "以上 N 个维度全部有明确答案，作为 Step 2 及之后所有步骤的输入" | 对齐结果留在对话里，后续步骤读不到 |
| **信息不足即声明** | 理解链："`slides.md` 未提供可靠信息时，直接说明无法从当前文件结构确认，不根据位置或颜色作确定结论" | 用位置/颜色脑补关系，输出看似合理的错误答案 |

### 3.2 需求对齐维度表（模板）

生成链只列了 4 个维度却声称 6 个（见 §6 缺陷 1），正确写法应是显式枚举：

| 维度 | 为什么必须问 | 缺失时的默认策略 |
|---|---|---|
| 主题 | 决定内容边界 | 不可默认，必须问 |
| 目标 | 决定取舍（说服 / 汇报 / 教学） | 从触发词推断，说明推断依据 |
| 受众 | 决定术语密度与调性 | 默认"同行专业人士"并声明 |
| 页数 | 决定信息密度与拆页 | 用户指定 > 大纲页数 > 自行推测并说明理由 |
| 交付场景 | 决定风格路由（会议 / 路演 / 答辩） | 走通用兜底 |
| 已有素材 | 决定是否联网、是否生图 | 无素材 → 触发联网搜索 |

设计要点：**每行都要写"缺失时怎么办"**。只写"必须明确"的表格，模型遇到缺失只能二选一——卡住或瞎猜。

### 3.3 产物驱动：把对齐结果固化成中间物

生成链不是"聊完就开工"，而是先产出 `DESIGN.md`，再按页执行：

- 全局 5 块：画布与安全区 / 配色方案（5 槽位 Hex 表）/ 字体系统 / 视觉母题 / 配图清单（文件·等级·生成方式·使用页）
- 每页 10 字段：`title` `type` `role` `rhythm` `layout` `visual` `visual_role` `density` `anti_pattern` `description`

三个收益：
1. **可检查**：完成检查直接对着字段挑错——"任意页缺少 `role`/`rhythm`/`visual_role`/`anti_pattern` 字段"即失败。
2. **抗漂移**：先定全局再逐页，避免做到第 8 页突然换配色。
3. **可交接**：换一个会话/换一个 agent，读 `DESIGN.md` 就能续做。

迁移建议：任何多步骤创作类 skill 都应该有一个中间 schema 文件，字段数控制在 6–12 个，且**每个字段都要能被机械校验**（枚举值、数量、是否存在）。

### 3.4 从"防止猜测"到"允许声明不确定"

理解链的处理最见功力：

- `inspect` 输出的 `### 结构` 只写**能确定的关系**：图表标注、带起止引用的连接线、源文件的"标题 + 正文"组。
- 线、箭头、自由形状、阶段色块**不写成关系**——宁可缺失，不可编造。
- 需要图片内容/连线方向/空间关系但材料没有时：**直接说无法确认**，并禁止"根据位置或颜色作确定结论"。

这套"输出侧约束"比"输入侧多问几句"更有效：文档格式本身不允许表达不确定，模型就只能省略；如果 schema 里有个 `relationship` 字段，模型一定会往里填东西。

**设计启示**：让"不知道"有合法表达位置（明确写"信息不足"的处置方式），否则模型会用编造填补空白。

### 3.5 双术语系统

| 场景 | 用词 |
|---|---|
| 对用户 | 内容大纲 / 风格设计 / 创建演示文稿 / 逐页制作 / 交付；页 / 封面 / 目录 / 这一页 |
| 对内部 | DSL / JSX / slidep / lint / upsert-dsl / OOXML / page_index |

并在严格约束里写成禁令："在 TODO / 进度汇报中**必须使用用户术语**……**禁止暴露内部实现**"。

这不是礼貌问题，是**需求理解问题**：汇报里出现 `lint` 会让用户以为要理解工具链，从而提出偏离目标的问题；统一说"检查页面"，用户反馈才会落在内容上。同理，`--page-index` 0-based、对用户页码 1-based，两者在文档里明确分开。

## 4. 简洁精确：怎么写出"不空洞"的规则

### 4.1 空洞的五种形态（skill 文档版）

| 形态 | 典型句子 | 为什么废 | 解药 |
|---|---|---|---|
| 无判据的形容词 | "注意版面美观、有设计感" | 模型无法判定是否达标 | 换成阈值 / 比例 / 数量 |
| 只写 what 不写 when | "要保证对齐" | 不知道什么情况下检查、检查到什么程度 | 补触发条件 + 判定阈值 + 返工动作 |
| 正例独舞 | 只贴一个漂亮例子 | 模型会模仿表面特征，不覆盖失败模式 | 必须配反例，且反例要**具体到数值** |
| 复述常识 | "PPT 要逻辑清晰""代码要可读" | 删掉后无任何信息损失 | 直接删 |
| 规则无优先级 | "简洁"与"信息完整"并列 | 冲突时随机选一个 | 标【硬】/【软】，并写冲突裁决 |

### 4.2 让规则可判定的四种写法

它 488 行的原则文件里，47 处禁令（含"严禁""不得""不许"）、19 行硬性标注，平均每 10 行一条硬约束。四种句式反复出现：

**（1）数字化**——把"适度"换成区间
> 页面 padding 上下 60px / 左右 60px（**均为硬下限，只能更大，不能更小**）；内容区 1160×600。

**（2）二选一判据表**——把"视情况而定"换成条件→动作
> | 分区间距 | 选用形式 |
> | 间距大（≥ 32px） | 细线（1px） |
> | 间距小（< 32px） | 留白 + 对齐 |

**（3）不等式链**——把"要有层次"换成可验算的关系
> 三级间距必须严格递增：段间距 < T < 分区间距 G；T 取值 L < T ≤ 2L。

**（4）具体反例**——把"避免 AI 味"换成可识别的形态清单
> 四类：形容词堆砌的卖点式标题（"卓越表现""行业领先"）；对称罗列 SWOT；万能句式（"随着 XX 的发展，YY 面临新的机遇与挑战"）；emoji / 装饰 icon 堆砌。典型反例：封面底部一排"61.2% 全月预估达成率 / 2500 万任务 / 1530 万预估 / 970 万缺口"。

注意反例的写法：**引用完整错误样本**，不是描述错误类型。描述类型仍要靠模型想象，贴样本可以直接比对。

### 4.3 改写对照（6 组，可直接拿去改自己的文档）

| # | 空洞写法 | 可执行写法 | 差在哪 |
|---|---|---|---|
| 1 | 注意留白，不要太空也不要太满 | 正文页内容区累计高度 ≥ 540px（600 的 90%）；常规内容页留白上限 35%；Hero 页允许 40–50% | 有基线、有上下限、有例外 |
| 2 | 标题和正文要有层次 | T > L 且 L < T ≤ 2L；段间距 < T < G，任一级被压平则层级失效 | 给变量、给不等式、给失效条件 |
| 3 | 颜色不要用太多 | 主色 ≤60% / 辅色 ≤30% / 强调 ≤10%；一页强调色 ≤2–3 处；文字色 ≤4 种；深色大块每页 ≤1 | 全部转成配额 |
| 4 | 避免 AI 味、避免模板感 | 禁用均分构图（等宽多栏、等大卡片网格）；相邻两页至少变 2 个维度；连续 3 页同构 → 硬失败 | 命名现象 + 给计数阈值 |
| 5 | 合理使用配图 | L1 ≥ 内容区 40%；L2 ≥ 280×180；L3 ≤ 64×64 且全篇同位；禁 200×70 标题右侧贴片 | 尺寸即判据 |
| 6 | 必要时询问用户 | 只问缺失的；一轮问完 ≤3 个；非硬阻塞按默认推进；意图未对齐禁止进入后续步骤 | 数量 + 门禁 + 默认策略 |

### 4.4 篇幅纪律

- **一处定义，多处引用**：字号规则只在 `design-principle.md §1.6` 定义，`general.md` 用一行"详见 §1.6"带过，并明确"本文件不重复"。复制规则 = 未来两处不一致。
- **硬软分级**：完成检查分两段——`❌ ...（违反必须返工）` 与 `软规则的自查（scenario 未定义时才检查）⚠️`。没有分级的清单，模型会把警告当错误，或者把错误当建议。
- **写完就停**：Step 6 只有一句"直接结束 PPT 生成流程，不要再做任何其余的动作（禁止复检、禁止截图等）"。**不写"最后再检查一遍"**，因为"再检查"是无界任务，会把已完成的闭环重新打开。

### 4.5 一句话自检："删掉测试"

逐条问：**删掉这句话，模型的行为会变吗？**

- 不会变 → 删（"要注意质量"）
- 会变但方向不明 → 补判据（"要对齐" → 对齐到哪条基准线、误差多少）
- 会变且方向明确 → 保留，并检查是否与别处冲突

## 5. 其他 12 条优秀实践

| # | 实践 | 具体做法 | 可迁移性 |
|---|---|---|---|
| 1 | **单页闭环** | 每页"配图 → 写页面 → 校验 → 提交"，未过不进下一页 | 任何批量生成场景，避免错误累积 |
| 2 | **顺序约束显式化** | "先写入 pptx 再 lint，禁止 upsert 前先 lint"——因为 lint 需要已存在的页码上下文 | 有依赖关系的工具调用，要把顺序写死 |
| 3 | **禁止自证** | "禁止主动调用外部工具截图和视觉检查（如 LibreOffice）；工具链已内置检查" | 模型最容易做的无效劳动，要明令禁止 |
| 4 | **术语隔离** | 对外"检查页面"，对内 `lint`；汇报禁用实现名 | 所有面向非技术用户的 skill |
| 5 | **状态对象踩坑写进文档** | `present_files` 返回的是地址不是 `file_id`；要用 `get_pool_status` 按同一路径取 UUID；已有 `file_id` 时不要重开 | 涉及会话状态的工具链，坑必须前置声明 |
| 6 | **失败阶梯** | `get_pool_status` 未命中 → 再 `present_files` 同路径查 → `open_file open_with_existing=true` → 与用户确认路径 | 不要只有一个 happy path |
| 7 | **单一脚本入口** | `edsdk.py list / schema / call`；"未设 `editor_sdk_port` 时探测 39099–39108" | 封装发现逻辑，别让模型拼端口 |
| 8 | **先 schema 再调用** | "用到一个查一个，不要一次性拉全量"；"未查直接拼参数属于流程违规"；"默认你没查过——先 schema，不要凭摘要猜" | 参数多的 API，禁止凭记忆 |
| 9 | **输出契约** | `{ok: true, ...}` / `{ok: false, error}` + 退出码；"失败信息必须落在 stdout（多数 Agent 只采集 stdout）" | 脚本要按调用方的采集方式设计 |
| 10 | **双轨场景** | 5 个垂直场景 + 1 个兜底；兜底文件首行声明定位，路由表给"是否明确属于"的判据 | 防止硬套垂直模板 |
| 11 | **硬闸门清单** | consulting 场景 17 条"出现任一情况必须返工"，含 7b/7c 细分 | 交付前终检，比"自查"有效 |
| 12 | **完成即止** | 交付后不做"顺手优化"，不重开已闭环的流程 | 抑制加戏 |

补充两条工程细节：
- **脚本内注释解释"为什么"**：`edsdk.py` 里 `ProxyHandler({})` 的注释写"绕开 http_proxy，否则 127.0.0.1 也可能被公司代理拦截导致超时"——这类非显然决策必须留痕，否则半年后会被"优化"掉。
- **产物可回溯**：`slides/NN.slide` 源文件与 pptx 并存，`assets/` 保留生成图。改稿可以回到源文件，而不是逆向编辑二进制。

## 6. 它的 6 个真实缺陷（反证上面的规范）

写规范容易，守规范难。这份 skill 自身就在跨文件引用上腐化了：

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | `create-from-scratch.md:37` | 声称"以上 **6 个**维度全部有明确答案"，但上面只列了 4 个（主题/目标/受众/页数） | 模型自行补 2 个或忽略 2 个，门禁形同虚设 |
| 2 | `design-principle.md:3` | 自称"被 `create-from-scratch.md` 的 **Step 2.2** 调用"，实际调用点是 Step 3.2 | 入口指针错位，按图索骥会读错阶段 |
| 3 | `dsl/image.md:38` | 引用"SKILL.md §配图获取策略"，而 SKILL.md 只有 18 行路由表，无此节 | 断链，规则实质丢失 |
| 4 | `dsl/image.md:42` | 引用 `scripts/extract.py`，实际文件是 `doc_image_extractor.py` | 断链，脚本无法执行 |
| 5 | `scenarios/general.md:283` | "每块有没有一眼可见的结论（见 §1.2）"，实际在 §2.2；`design-principle.md:270` 又把"数据落判断"指成 1.1（实际 2.1） | 章节号漂移，读者定位失败 |
| 6 | `design-principle.md:74` | §1.4 条目编号从 **3** 开始（1、2 缺失） | 编辑残留，暴露未做结构校验 |

共同点：**全部是"改了正文没改指针"**。这正是分层架构的代价——文件越多，交叉引用越多，腐化越快。

### 交叉引用审计（建议纳入 CI / 提交前检查）

```bash
cd <skill_dir>

# 1) 所有 markdown 链接目标是否存在
grep -rhoE '\]\(([^)]+\.md)\)' . | sed 's/](//;s/)//' | sort -u | while read f; do
  [ -e "$f" ] || echo "MISSING LINK: $f"
done

# 2) 所有反引号里的本地脚本路径是否存在
grep -rhoE '`(scripts|references)/[A-Za-z0-9_./-]+`' . | tr -d '`' | sort -u | while read f; do
  [ -e "$f" ] || echo "MISSING PATH: $f"
done

# 3) 所有 §x.y 章节引用是否有对应标题
grep -rhoE '§[0-9]+(\.[0-9]+)?' . | tr -d '§' | sort -u | while read n; do
  grep -qE "^#{2,4} *${n}[ .、]" references/design-principle.md || echo "MISSING SECTION: §$n"
done
```

这三条命令能在提交前抓到上表 6 个缺陷里的 5 个。

### 7.1 结构（11 项）

- [ ] `SKILL.md` 正文 ≤ 40 行（frontmatter 不计），只有路由表与跨链约束
- [ ] 头部六字段齐全：`name` / `display_name_zh` / `display_name_en` / `description` / `description_en` / `version`

## 8. 一页纸总结

一个生产级 skill 的形态是：**极薄的路由 + 按意图分支的流程 + 按使用时机分层的知识 + 单一入口的执行脚本**，头部用双语六字段交代自己是什么、什么时候该用。

它的质量来自三个动作，而不是来自篇幅：

1. **把模糊要求翻译成可测量的判据**（60px、≥540px、≤4 种、G ≥ 2T）
2. **把"不要猜"翻译成门禁与默认策略**（未对齐禁止越步、只问缺失、一轮 ≤3、信息不足就明说）
3. **把"做好了"翻译成机读校验**（lint diagnostics、DESIGN.md 字段表、17 条返工闸门）

反面同样清晰：**没有判据的原则、没有配额的约束、没有审计的引用，都会在三次迭代内退化成正确但无用的废话。**
