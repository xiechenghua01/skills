# 生成链

从意图写到合规文本。先定三件事——文体、档位、文本类型——再动笔。这三件事定错，后面每条规则都会用错。

```
判文体 → 判档位 → 判文本类型 → 写 → 自检 → 交付
```

---

## Step 1 判文体

| 用户要什么 | 文体 | 模板 |
|---|---|---|
| 梳理需求、下发开发任务、写技术规格 | 需求下发 | [模版 1](references/templates.md) |
| 写代码注释、异常断言、重构注释 | 代码注释 | [模版 2](references/templates.md) |
| 写技术方案、架构选型、ADR | 架构方案 | [模版 3](references/templates.md) |
| 汇报进度、给排查结论、交付说明 | 闭环汇报 | [模版 4](references/templates.md) |

四种文体的硬要求不同，**不要混写**：一份需求里不要夹汇报语气，一份 ADR 里不要写过程流水账。

## Step 2 判档位

| 信号 | 档位 |
|---|---|
| 用户没说 STE、只是要「写清楚点」 | pragmatic |
| 用户点名 `ste` / `STE`，或要求「合规」「审计」「按规范」 | strict |

拿不准时按 pragmatic 写，并在交付说明里写一句「按 pragmatic 档写；需要 strict 请说一声」。

## Step 3 判文本类型

**这一步决定句长上限和动词形式，必须在写之前定。**

| 类型 | 判据 | 句长上限 | 动词形式 |
|---|---|---|---|
| 程序性 | 告诉读者「怎么做」：步骤、命令、操作序列 | 单句 ≤ 30 字 | 祈使句，一步一句 |
| 描述性 | 告诉读者「是什么、为什么」：机制、约束、背景 | 单句 ≤ 40 字 | 陈述句，主动语态 |

一份文档里可以两种都有，但**同一段不要混**：步骤里的说明写成描述句，或者说明里插一步操作，都会让读者分不清该做还是该懂。

---

## Step 4 按文体写

### 4.1 需求下发

1. **条件在前，动作在后**：先写触发条件与业务边界，再写要做什么。
2. **锁定改动范围**：写明允许改的路径与模块，以及禁止触碰的敏感区域。
3. **强制验收命令**：写出静态检查与测试的确切命令，不写「确保通过」。
4. **阻断点封闭化**：需要用户决策时给编号选项，每项写动作与代价。

### 4.2 代码注释

1. **不复述代码字面**：不写「遍历数组」「判断是否为空」。
2. **只记物理限制与隐性契约**：前置条件、并发边界、耗时阈值、历史故障规避点。
3. **异常断言三要素**：`[确切现象] + [期望值 vs 实际值] + [恢复动作]`，缺一不可。
4. **能靠命名说清的就不写注释**：注释是最后手段，不是标配。

### 4.3 架构方案 / ADR

1. **结论前置**：首句就是选型结论，不写背景铺垫。
2. **指标定量**：把「高并发」「易扩展」换成 QPS、P99、内存上限、恢复时间。
3. **如实记代价**：写采用方案的伴随代价，以及被否决方案与被否决原因。
4. **跨 3 个以上模块的流程配图**：用 Mermaid 时序图或状态机图，文字只定义术语与刚性约束。

### 4.4 闭环汇报

1. **首句写状态**：格式 `<执行态>：<范围>。<验证态>：<范围>。`
2. **证据可定位**：改动精确到 `路径:行号`，验证引用真实命令与输出。
3. **未做事项单列**：写清物理原因，不用「后续再补」含糊带过。
4. **不写流水账**：不叙述「我先……然后发现……」，直接给结论与证据。

---

## Step 5 写法约束

| 项 | 要求 |
|---|---|
| 句长 | 步骤句 ≤ 30 字，描述句 ≤ 40 字；汉字计 1，英文词/数字/标识符计 1，标点不计 |
| 语态 | 主动语态，明确执行主体；不写「被系统自动清空了」 |
| 双重否定 | 禁止；「不能不确认」改为「必须确认」 |
| 名词串 | 连续修饰不超过 3 个名词，超了用助词拆开 |
| 列举 | 3 项以上拆成列表，不用逗号连成长句；不用「等等」「之类」收尾 |
| 标点 | 中文全角 `，。；：（）`；强调与界面文本用直角引号 `「」` |
| 代码 | 标识符、命令、路径写在反引号内 |
| 盘古之白 | 中文与英文字词、数字之间留一个半角空格；中文与全角标点之间不留 |
| 术语 | 一词一义：选定一个词，全文不再换同义词 |

---

## Step 6 自检

**门禁。** 两条都要过：

```bash
python3 <skill 目录>/scripts/validate_ste.py <文件> --mode strict   # strict 档
python3 <skill 目录>/scripts/validate_ste.py <文件>                 # pragmatic 档
```

脚本只覆盖 8 条机械可判的规则，剩下的靠人工。逐条对照 [references/coverage.md](references/coverage.md) 里的「人工」行，至少核这几项：

- 一词一义：全文有没有把同一个东西叫了两个名字。
- 一段一主题：有没有一段里讲了两件事。
- 结论前置：首句是不是结论。
- 证据可定位：引用的路径、行号、命令是否真实存在。

**脚本零错误不等于合规**，只等于「没踩机械可判的坑」。

## Step 7 交付

交付说明写四件事：文体与档位、脚本结果（错误/告警数）、人工核过哪几条、「未确认」项。

**到此结束。** 不要顺手把用户的原文也改了，也不要在没被要求时切换档位。

---

## 完成清单

- 文体、档位、文本类型三个判断都做了，且有依据。
- 句长按文本类型区分，不是一律 40 字。
- 情态词与状态词按档位执行；strict 档下没有漏网的近义词。
- 脚本跑过且零错误；人工核过语义规则。
- 交付说明写了档位与未确认项。
