# STE-ZH 受控词典与排版规范（Terminology）

本文档定义简化技术中文（STE-ZH）的核准词汇、禁止词汇、去虚化动词对照表与中英文混排规范。

---

## 一、 严格受控的三大情态词

全文仅允许使用以下 3 个情态词，严禁替换为近义词：

| 情态词 | 唯一核准词义 | 严禁使用的近义词 / 替换词 | 适用示例 |
| :--- | :--- | :--- | :--- |
| **必须** | 强制性动作或必要条件 | 应、应当、应该、需要、务必、要、需 | 接口超时时间**必须**设置为 3 秒。 |
| **不得** | 绝对禁止性约束 | 不应、不要、避免、禁止、切勿、不允许、严禁 | 任何业务逻辑**不得**在主线程执行耗时 IO。 |
| **可以** | 允许执行，非强制要求 | 可、能够、允许、可选 | 客户端**可以**选择携带跟踪头部。 |

### 豁免规则
1. 「需要」在表示客观“缺少依赖或某项输入”时不受限（如：“系统需要 4GB 物理内存才能冷启动”）。
2. 在作为章节固定标签「要做」时不受限。
3. 引用外部字面量、日志报错或他人原话时，保留原词并在引号内注明。

## 二、 严格受控的 10 个状态词（执行与验证解耦）

技术交付与工作汇报中，必须严格区分**执行态**与**验证态**，禁止混为一谈。

### 1. 执行状态词（6 个）
| 状态词 | 规范释义 | 严禁使用的替代词 |
| :--- | :--- | :--- |
| **未开始** | 尚未执行任何实际物理操作。 | 待办、TODO、未动 |
| **进行中** | 动作已发起，尚未完全结束。 | 处理中、跟进中、搞着呢 |
| **部分完成** | 仅完成了指定目标的一部分，必须明确列出未完成范围。 | 大致完成、基本搞定 |
| **已完成** | 所述范围的动作全部执行完毕。**绝不单独表示已验证**。 | 搞定、OK、done、弄完了 |
| **跳过** | 经评估后明确不予执行，必须附带原因。 | 忽略、略过 |
| **阻塞** | 缺少前置条件或物理依赖，无法继续，必须说明阻断原因。 | 卡住、受阻 |

### 2. 验证状态词（4 个）
| 状态词 | 规范释义 | 严禁使用的替代词 |
| :--- | :--- | :--- |
| **已验证** | 指定范围的测试/检查已执行且结果全通过，必须附带命令与输出。 | 已测试、跑过了、没毛病 |
| **未验证** | 已知没有执行该项验证，必须附带未验证原因。 | 理论可行、应该没问题 |
| **失败** | 动作或验证已执行，但结果不符合预期，必须附带失败日志或退出码。 | 报错、有点小问题 |
| **未确认** | 事实缺少足够证据，无法断言真伪，必须附带进一步确认的方法。 | 疑似、可能、大概是 |

### 状态解耦红线
- ❌ 违规：「已完成全部代码修改，且修复了并发缺陷。」（未提供测试证据，偷换了完成与验证）
- ✔️ 规范：「已完成：重构订单锁定逻辑。未验证：本地缺少高并发压测环境。」

## 三、 虚化动词清洗对照表

严禁使用没有具体物理动作的“虚化动词短语”，必须提炼为明确的直接动作：

| 严禁使用的虚化表达 | 必须采用的直接动词改写 |
| :--- | :--- |
| 对配置**进行**修改 / 调整 | **修改 / 调整**配置 |
| **开展**单元测试编写**工作** | **编写**单元测试 |
| **落实**系统安全加固**措施** | **加固**系统安全 |
| **做好**上线前的准备 | **检查**上线依赖项 |
| **实现**登录鉴权**功能** | **增加**登录鉴权 |
| 对数据**予以**删除 / **加以**记录 | **删除**数据 / **记录**数据 |
| **通过**消息队列的**方式**发送 | **使用**消息队列发送 |
| **作出**回滚**决定** | **决定**回滚 |
| 接口**存在**超时**问题** | 接口响应时间超过 5 秒 |
| 系统有**一定的 / 较大的**延迟 | 系统延迟达到 450ms（必须给量；无量则删除修饰词） |

## 四、 模板与文档固定用词规约

在撰写方案、报告与规范文档时，以下章节标题和标签词汇必须统一，不得随意更换同义词：

| 受控标题 / 标签 | 严禁替换为 | 语义定位 |
| :--- | :--- | :--- |
| **术语** | 名词解释、词汇表、定义 | 定义本文独有的专业概念与缩写 |
| **共同条件** | 前提、背景、通用约束 | 描述全文统一生效的前置依赖 |
| **问题** | 现状、缺陷描述、痛点 | 描述客观物理故障或业务瓶颈 |
| **要做** | 方案、措施、修复内容、TODO | 描述接下来准备执行的具体动作列表 |
| **改动** | 变更内容、修改点、diff | 描述已经发生的具体代码或配置变更 |
| **验证** | 测试情况、自测、检查结果 | 描述运行检查的具体命令、覆盖与结果 |
| **未做** | 遗留、后续、延后 | 明确界定不在本次范围内的任务 |
| **现象** | 表现、症状、问题表象 | 描述客观监控指标或错误报错 |
| **原因** | 根因分析、问题所在 | 描述导致现象的根本技术诱因 |
| **证据** | 依据、出处、佐证 | 引用行号、Commit Hash 或日志条目 |
| **建议** | 方案、解决思路 | 提出针对该问题的确切处理动作 |
| **待确认** | 风险、TBD、遗留问题 | 需要进一步核实证据或决策的事项 |
| **推荐** | 建议选择、首选、优先 | 标注在第一选项后的推荐倾向 |

## 五、 标点与混排规范（Pangu Spacing & Punctuation）

1. **标点全半角准则**：
   - 中文正文主体使用全角标点：`，。；：（）`。
   - 界面文案、引用原话或强调文本使用直角引号：`「」`，不使用弯双引号 `“”`。
   - 代码标识符、路径、环境变量、命令与技术参数一律写在反引号内：`` `user_id` ``、`` `npm test` ``。
2. **盘古之白（空格规范）**：
   - 中文字符与半角英文字母、数字之间**必须保留一个半角空格**。
     - ✔️ 正确：系统处理了 1000 个请求。
     - ❌ 错误：系统处理了1000个请求。
   - 中文字符与全角标点之间**不得加空格**。
   - 反引号包裹的代码块与相邻汉字之间**必须保留一个半角空格**。
     - ✔️ 正确：调用 `getUser()` 接口获取实体。
     - ❌ 错误：调用`getUser()`接口获取实体。
